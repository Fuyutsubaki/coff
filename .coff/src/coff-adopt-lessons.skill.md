## 入力

反省の一覧。形式は問わない（会話中の箇条書き、ユーザの一言、coff-log-investigate skill の報告の「教訓候補」節）。本体セッションで実行する（手順 1 で会話中の発言に当たるため、subagent に委譲しない）。

## 手順

1. 反省を 1 件ずつ元の発言と突き合わせる。会話中に発言があれば引用する。AI が要約した一覧しか無ければ、件ごとに元の意図を一問で確かめる（推奨案を添えて、一問ずつ）。 <!-- AI が生成した一覧は元の意図が曲解されていることがある。却下する前に元の発言に当たる -->
2. 各件を 3 つに仕分ける。まず「必要か否か」で判断し、「既存 skill に置き場がない」は却下理由にしない（必要なら置き場は作ってよい）。
   - 規範: 同じ状況で同じ失敗が再び起きる構造的な問題で、手順や判定基準の一文として書けるもの。採用先は `.coff/src/` の既存 skill の該当箇所。
   - issue: 一文では済まず、実装や構造の変更が要るもの。
   - 不採用: 一度きりの事故、または既存 skill に実装済みのもの（該当箇所を示す）。

   記録済みの設計判断（skill 冒頭のコメントや issue の「人間が決めた判断」）と衝突する件は、衝突先を添えて提示する。どちらを取るかは人間が決める。
3. 1 件 1 行で提示し、人間の採否を得る。行の形は「反省 / 仕分け / 採用先または却下理由（衝突があれば衝突先も）」。採用先は skill 名と節まで書く。理由の記録は coff-detail-issue の「判断の記録」規範に従う。ここまでは `.coff/src/` に触れない。
4. 採否が出てから採用分を実行する。
   - 規範: 1 件ずつ問題空間だけの issue を coff-issue-create で起こし、`.coff/src/` に追記し、`/coff-compile`（ラッパー `/compile` があればそれ）でビルドし、coff-issue-done で閉じる。polish は通さない。 <!-- detail の受け入れ基準「単体の小さな変更は数行の問題空間だけの issue で直ちに done にしてよい」に当たる -->
   - issue: coff-issue-create で起票して終える。polish 以降は別途。
5. 報告する: 追記先、起票した issue、不採用と要判断の件とその理由。

## 出口基準

- 採用分が `.coff/src/` か issue に残り、採否の理由が記録されていること。
