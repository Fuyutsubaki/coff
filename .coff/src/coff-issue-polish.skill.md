## 手順

1. `.claude/skills/coff-detail-issue/SKILL.md` を読み込み、テンプレートと品質基準を把握する。 <!-- skill は自動では相互ロードされないので明示的に読む -->
2. 対象 issue を読み、まず問題空間を点検する。問題の妥当性4観点を満たし問題が正しく立っているか確かめ、崩れていれば「背景・目的 / 現状」を立て直す（問題空間への差し戻し）。あわせて、独立に採否・完了を判断できる問題が複数含まれていないかを検査し、含まれていれば分割を提案する（1 issue = 1 意図。detail の目的節に従う）。ユーザーが明示的に束ねる指示をした場合は従い、その事実と理由を「人間が決めた判断」に記録する。
3. コード調査: 関連ファイル、既存実装、依存、関連 skill・ドキュメント・関連 issue を実際に読み、「現状 / 実装詳細」を事実に基づいて埋める。
4. 前提検証をチェックリストで行う: 記載の前提が現在のコードと矛盾しないか / 参照するファイルパスが実在するか / 検証の各条件が確認手段つきで実行可能か。矛盾は修正し、要判断点は「リスク・未解決」に移す。
5. 論点の仕分け。詰める過程で出る論点を「コードで答えが出る」「ユーザーの判断が要る」に分ける。前者は手順3-4で自分で調べて解決し、人間には聞かない。後者だけ確定前に聞く。聞くときの規律: 一問ずつ聞く、各問に推奨案を添える、コードで分かることは聞かずに自分で調べる。問答の出口は「汎用的な合意」ではなく「この issue が単体で実装可能になること」に置く。人間が決めた判断は「人間が決めた判断」セクションに記録する。決め打ちで仕様化しない。
6. 解決空間を詰める。変更方針には採用案に加え、検討した代替案と却下理由を集約する（却下案や決定の実体を他の節に書かない）。検証は各条件に確認手段を併記する形式で埋める。実装詳細には触る範囲と代表的なファイルパスを含め、スキルやコードの手順を丸写しせず参照で済ませ、すぐ古くなるファイルパス列挙をしない（detail の基準に従う）。
7. （必要なら）試験実装。実現可能性が不確かな箇所は小さく試して確かめる。安全手順:
   - 着手前に `git stash` で作業ツリーを退避し、確認後 `git stash pop` か破棄で戻す。
   - 別プロセスで実行する場合は codex-delegate skill に委譲し、結果だけ回収する。
   - いずれも試験実装の成果物は、issue ファイルへの追記以外はコミットに含めない。
8. 自己レビューをチェックリストで行う: テンプレ各節が埋まっているか / 検証の各条件に確認手段が付き実行可能か / 前提とコードが一致するか / リスクを網羅したか / ユーザーに聞くべき論点を黙って決め打ちしていないか / 実装者が迷う箇所はないか / 後で読む人に無用な・すぐ古くなる情報を書いていないか / 却下案や決定の実体が変更方針の外に散っていないか / 文体が coff-japanese-tech-writing の規範に従い、スラッシュや入れ子括弧で詰め込んだ文を残していないか。
9. 仕上げに冒頭の「要約」節（2、3行: 何をなぜどう変えるか）を書き、issue ファイルを上書き更新する。先頭の frontmatter（`status` を含む）は保存し、`status` の値は変えない（完了判断は coff-issue-done の責務）。日本語の文章は coff-japanese-tech-writing skill の規範に従い、論証の筋は coff-argument-gap-edit skill で点検する。
10. 実装者シミュレーションを行う。新鮮なコンテキストのサブエージェントを起動し、更新した issue ファイルだけを読ませて次の4点を返させる: 実装計画の骨子 / 着手を妨げる点 / 曖昧な点 / 検証の各条件が実行可能か。polish セッションの会話文脈は渡さない（リポジトリの読み取りは許す。実装者もリポジトリは読める前提）。指摘を解消して issue を上書きし、再実行する。上限は2周とし、解消しない点は「リスク・未解決」に明記する。的外れな指摘は採らずに捨て、指摘への防御で issue を膨らませない。 <!-- 代替手段は codex-delegate。ネイティブのサブエージェントを既定にするのは plugin 依存を避けるため（issue/2026/07/1518-polish-implementer-sim.md の判断） -->
11. 適用した変更点と残課題を報告する。

## 仕上がり基準

- 実装者が issue だけで着手できること。
