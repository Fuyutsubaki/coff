## 手順

1. `.claude/skills/coff-detail-issue/SKILL.md` を読み込み、テンプレートと品質基準を把握する。 <!-- skill は自動では相互ロードされないので明示的に読む -->
2. 対象 issue を読み、まず問題空間を点検する。問題の妥当性4観点を満たし問題が正しく立っているか確かめ、崩れていれば「背景・目的 / 現状」を立て直す（問題空間への差し戻し）。
3. コード調査: 関連ファイル、既存実装、依存、関連 skill・ドキュメント・関連 issue を実際に読み、「現状 / 対象範囲 / 実装詳細」を事実に基づいて埋める。
4. 前提検証をチェックリストで行う: 記載の前提が現在のコードと矛盾しないか / 参照するファイルパスが実在するか / 受け入れ条件が検証可能か。矛盾は修正し、要判断点は「リスク・未解決」に移す。
5. 論点の仕分け。詰める過程で出る論点を「コードで答えが出る」「ユーザーの判断が要る」に分ける。前者は手順3-4で自分で調べて解決し、人間には聞かない。後者だけ確定前に聞く。聞くときは `.claude/skills/grilling/SKILL.md` を読み、その規律に従う。問答の出口は「汎用的な合意」ではなく「この issue が単体で実装可能になること」に置く。人間が決めた判断は「人間が決めた判断」セクションに記録する。決め打ちで仕様化しない。
6. 解決空間を詰める。変更方針には採用案に加え、検討した代替案と却下理由を残す。受け入れ条件・テスト方針も埋める。実装詳細はスキルやコードの手順を丸写しせず参照で済ませ、すぐ古くなるファイルパス列挙をしない（detail の基準に従う）。
7. （必要なら）試験実装。実現可能性が不確かな箇所は小さく試して確かめる。安全手順:
   - 着手前に `git stash` で作業ツリーを退避し、確認後 `git stash pop` か破棄で戻す。
   - 別プロセスで実行する場合は codex-delegate skill に委譲し、結果だけ回収する。
   - いずれも試験実装の成果物は、issue ファイルへの追記以外はコミットに含めない。
8. 自己レビューをチェックリストで行う: テンプレ各節が埋まっているか / 受け入れ条件は検証可能か / テスト方針は十分か / 前提とコードが一致するか / リスクを網羅したか / ユーザーに聞くべき論点を黙って決め打ちしていないか / 実装者が迷う箇所はないか / 後で読む人に無用な・すぐ古くなる情報を書いていないか。
9. issue ファイルを上書き更新する。先頭の frontmatter（`status` を含む）は保存し、`status` の値は変えない（完了判断は coff-issue-done の責務）。日本語の文章は japanese-tech-writing skill の規範に従い、論証の筋は argument-gap-edit skill で点検する。適用した変更点と残課題を報告する。

## 仕上がり基準

- 実装者が issue だけで着手できること。
