## 手順

1. `.claude/skills/coff-detail-issue/SKILL.md` を読み込み、テンプレートと品質基準を把握する。 <!-- skill は自動では相互ロードされないので明示的に読む -->
2. 対象 issue を読み、まず問題空間を点検する。問題の妥当性4観点を満たし問題が正しく立っているか確かめ、崩れていれば「目的 / 現状」を立て直す（問題空間への差し戻し）。あわせて、独立に採否・完了を判断できる問題が複数含まれていないかを検査し、含まれていれば分割を提案する（1 issue = 1 意図。detail の目的節に従う）。
3. コード調査: 関連ファイル、既存実装、依存、関連 skill・ドキュメント・関連 issue を実際に読み、「現状 / 実装詳細」を事実に基づいて埋める。外部資料の調査結果は「調査記録」に出典つきで書く。
4. 前提検証をチェックリストで行う: 記載の前提が現在のコードと矛盾しないか / 参照するファイルパスが実在するか。矛盾は修正し、ユーザーの判断が要る点は「未決」に移す。
5. 論点の仕分け。詰める過程で出る論点を「コードで答えが出る」「ユーザーの判断が要る」に分ける。前者は手順3-4で自分で調べて解決し、人間には聞かない。後者だけ確定前に聞く。聞くときの規律: 一問ずつ聞く、各問に推奨案を添える、コードで分かることは聞かずに自分で調べる。問答の出口は「汎用的な合意」ではなく「この issue が単体で実装可能になること」に置く。決まった論点は「未決」から消し、ユーザーが選んだ結論は「決めたこと」に書いて設計方針に展開する。決め打ちで仕様化しない。
6. 解決空間（設計方針 / 完了条件 / 実装メモ）を detail のテンプレート規則に従って書く。設計方針には採用案とその理由、検討した代替案と却下理由、対象外を集約し、他の節に散らさない。実装メモは detail の「残す / 溜めない」の基準に従う。
7. （必要なら）試験実装。実現可能性が不確かな箇所は小さく試して確かめる。安全手順:
   - 着手前に `git stash` で作業ツリーを退避し、確認後 `git stash pop` か破棄で戻す。
   - 別プロセスで実行する場合は codex-delegate skill に委譲し、結果だけ回収する。
   - いずれも試験実装の成果物は、issue ファイルへの追記以外はコミットに含めない。
8. タイトル直下の要約（2、3 行: 何をなぜ）を必要なら更新し、issue ファイルを上書き更新する。旧テンプレートの issue（`## 要約` `## 人間が決めた判断` などがある）なら、新テンプレートの構成に書き換える。先頭の frontmatter（`status` を含む）は保存し、`status` の値は変えない（完了判断は coff-issue-done の責務）。日本語の文章は coff-japanese-tech-writing skill の規範に従い、論証の筋は coff-argument-gap-edit skill で点検する。
9. 清掃。書き出した issue の全文を detail のテンプレート規則と polish の出口基準に照らして点検し、直して上書きする。引き継いだ記述だけでなく、今回のセッションで書いた分も対象にする。後で読む人に無用な情報と、すぐ古くなる情報は消す。加えて次を見る。 <!-- 書き出しの後に置くのは、要約とタイトルがそこで確定するため。点検の対象を挙げるのは、「後で読む人に無用な情報を書いていないか」という問いだけでは何も見つからなかったため。書き出し前の自己レビューもここにまとめた。issue/2026/09/2118-polish-cleanup-and-review.md の判断 -->
   - 決め打ち: ユーザーに聞くべき論点を黙って決め打ちしていないか。
   - タイトルと要約: 経緯を語っていないか。
   - 決めたこと: 今有効な決定の一覧になっているか。
   - 完了条件と確認手段: 今回の決定で崩れた前提に立っていないか。
   - 却下理由: 実際にその案への反論になっているか（案の前提の取り違えや、案と無関係な一般論は書き直すか削る）。
   - 却下理由と実装メモ: 以前の実装や以前の polish の語彙と前提が残っていないか。
   - 折り目より上の行数: `## 実装メモ` の行番号が目安以下か。超えていれば直す。残課題として報告しない。
10. 実装者シミュレーションを行う。新鮮なコンテキストのサブエージェント（会話を継承する fork ではない）を起動し、更新した issue ファイルだけを読ませて次の4点を返させる: 実装計画の骨子 / 着手を妨げる点 / 曖昧な点 / 完了条件の各条件が実行可能か。polish セッションの会話文脈は渡さない（リポジトリの読み取りは許す。実装者もリポジトリは読める前提）。指摘の解消は原則「実装メモ」に書き（手順の曖昧さは「完了条件の確認手段」へ。実装詳細に手順を書かない）、折り目より上は完了条件・設計方針・決めたこと・未決が実際に変わるときだけ動かす。issue を変更したときだけ上書きして再実行する。上限は2周とし、解消しない点のうちユーザーの判断が要るものは、手順 5 の規律でその場で聞いて確定させる（未決に残して終えない）。的外れな指摘は採らずに捨て、指摘への防御で issue を膨らませない。 <!-- 代替手段は codex-delegate。ネイティブのサブエージェントを既定にするのは plugin 依存を避けるため（issue/2026/07/1518-polish-implementer-sim.md の判断） -->
11. レビューを 1 回受ける。新鮮なコンテキストのサブエージェントを観点ごとに並列に起動し、issue ファイルと、最後のシミュレーションが返した実装計画の骨子だけを渡す。条件はシミュレーションと同じにする（fork を使わない、会話文脈を渡さない、リポジトリの読み取りは許す）。ファイルの修正と、担当する観点の外の指摘はさせない。 <!-- 実装後のレビューで初めて見つかる設計の問題を、実装の前に拾うための段。観点は coff-review-diff-code のうちコードが無くても判定できるものに、記録としての質を足した。issue/2026/09/2118-polish-cleanup-and-review.md の判断 -->

    観点:

    1. YAGNI（未使用の拡張点、担保済みの再チェック、過剰な保険）
    2. 仕様が無意味に複雑でないか
    3. 目的と変更の規模が釣り合っているか
    4. issue が求めるユーザー入口（skill / CLI / UI）が計画に含まれているか。その入口が仕様の写しで肥大していないか
    5. 記録としての質（経緯の記述、節どうしの矛盾、古い前提）。この観点のサブエージェントには、基準として手順 1 と同じ detail のファイルを読ませる

    指摘は手順 5 の仕分けで扱う。的外れな指摘は捨て、判断の要らないものは直し、ユーザーの判断が要るものはその場で聞いて確定させる。直す場所は折り目の上下を問わない。設計方針か完了条件を変えたら、手順 10 のシミュレーションを 1 回だけやり直す（上限の 2 周とは別に数える）。最後に、清掃の後に直した箇所を手順 9 の項目で点検し直す。
12. 適用した変更点と残課題を報告する。

## 仕上がり基準

- detail の polish の出口基準を満たすこと。
