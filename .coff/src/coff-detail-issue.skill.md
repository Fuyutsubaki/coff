## 直接呼び出し時の動作

`/coff-detail-issue` が直接呼ばれたときは、以下の目的、保存先、命名規則、テンプレート、品質基準を提示するだけにとどめる。issue の生成も編集もしない（生成は coff-issue-create、磨き込みは coff-issue-polish の役目）。

## 目的

issue は AI と人間が共有する作業単位の記録である。open の間は実装契約（実装者が issue だけで着手できる仕様書）として読み、done 後は設計判断の長期記憶として読む。

open の間の主要読者はユーザー本人で、折り目（`## 実装メモ`）より上を数分で読む。実装 AI は折り目より下も読んで着手する。「決めたこと」節と polish の論点仕分けは、AI と人間の判断の境界を本文に残すための仕組みである。 <!-- 主要読者をユーザーに置いた判断。issue/2026/09/1413-issue-template-for-human-reader.md -->

記録の正しさは、master に入った時点の内容で判定する。ブランチ上では、コミット済みの issue も追記ではなく書き換えてよい。 <!-- ブランチ内の履歴は後世の master から見ればどうでもいい歴史。「issue は記録だから追記で扱う」という縛りは採らない。issue/2026/07/2701-master-view-record.md の判断 -->

入口基準:

- すべての変更は issue を通す。チーム開発で PR を通すのと同じ強さの運用とする。
- issue の単位は「1つの意図」であり、PR 並みに粗くてよい。独立に採否・完了を判断できる問題は束ねない。例: 表記ゆれの一括修正は多数ファイルに触れても1意図だが、互いに独立な複数の整備は束ねない。
- 作業中の issue の意図に従属する軽微修正は、その issue に同乗してよい。
- 単独の軽微な変更は、問題空間だけの数行の issue を即立てて即 done にしてよい。

チームの issue 管理（優先度、担当、期限）は担わない。

## 保存先と命名

- issue はリポジトリ内の `issue/<yyyy>/<mm>/` ディレクトリに置く（作成した年月で振り分ける）。1 件の issue につき 1 つの Markdown ファイルとする（GitHub Issues は使わない）。
- ファイル名は `<ddHH>-<slug>.md`（`dd`=日、`HH`=時。年月はディレクトリが表すので接頭辞には含めない）。`<slug>` は内容を表す短いケバブケース（例 `fix-hoge`、`add-login`）。
- 保存先とファイル名の例:

  ```bash
  dir="issue/$(date +%Y/%m)"   # 例: issue/2026/07
  ts="$(date +%d%H)"           # 例: 0222
  mkdir -p "$dir"
  # <slug> は内容を表す短いケバブケース。例: fix-hoge
  # -> issue/2026/07/0222-fix-hoge.md
  ```

## 状態（status）

issue の完了状態は、ファイル先頭の YAML frontmatter に `status` として持つ。

- 値域は `open`（未完了）と `done`（完了）の2値。
- 新規 issue は coff-issue-create が `status: open` を付けて生成する。
- 完了時は coff-issue-done が `status: done` へ更新する。
- frontmatter が無い、または `status` が無い issue は `open` とみなす（既存 issue を触らずに済ませるための既定）。

完了しても issue ファイルは元の場所に残す。<!-- ファイルパスを変えないので、issue 間の相互参照は壊れない。 -->

完了の文脈（いつ、どの変更で完了したか）は issue に記録せず、git から辿る。 <!-- git から導出できる情報を frontmatter に書くと二重管理になる。issue/2026/07/1518-done-evidence.md の判断 -->

```bash
git blame -L '/^status:/,+1' -- <issueファイル>   # 完了コミットと日時
gh pr list --search <ハッシュ> --state merged      # そのコミットを含む PR = 実装の所在
```

前提として、done への変更と実装は同じ PR に入れる。 <!-- これが崩れると PR 経由で実装に辿れなくなる -->

一覧（状態、パス、タイトル）は coff-issue-list が都度生成する。一覧ファイル（README など）は置かない。 <!-- 置くと陳腐化する。issue/2026/09/1413 の判断 -->

## 言語

issue 本文は日本語で書く。日本語は coff-japanese-tech-writing skill の規範に従って書く。ただし issue は仕様書なので、参照するファイル名、関数名、識別子は具体名で書く。同 skill の「後で参照する必要のない固有名を出さない」規則は issue には適用しない。

## 問題空間と解決空間

issue は「問題を立てる」段と「解を詰める」段で作る。役割はこの軸で分ける。

- 問題空間（要約 / 目的 / 現状）は coff-issue-create が立てる。
- 解決空間（設計方針 / 完了条件 / 実装メモ）は coff-issue-polish が詰める。
- 横断（決めたこと / 未決）は両段で書き足す。

### 問題の妥当性

create が問題を立てるときも、polish が入口で問題を点検するときも、次の観点で妥当性を吟味する。

- 本当に解くべき問題か。
- すでに解決していないか。
- 問いの立て方は適切か。
- 別の捉え方はないか。

棄却した捉え方は、create の段では目的に「扱わない」と一文で残し、polish が設計方針の対象外に集約する。ユーザーの判断が要る疑いは「未決」に置く。

## テンプレート

新規 issue は次の構成で書く。

```markdown
---
status: open   # open（未完了）| done（完了）
---
# <タイトル: 命令形で簡潔に>

<要約 2、3 行: 何を、なぜ>

## 目的
<解きたい問題と、解けたときの状態。扱わないことがあれば一文で>

## 現状
<コードと運用の事実。ファイル名や関数名で指す。外部資料の調査は書かない>

## 設計方針
<採用案と理由。却下した代替案は理由を一言添えて箇条書き。対象外を明示する>

## 決めたこと
- <決定>（<理由の要点。ユーザーの語彙で>）

## 未決
- <ユーザーの判断待ちの論点>

## 完了条件
- [ ] <完了の条件>

## 実装メモ

### 実装詳細
<触る範囲と代表的なファイルパス、手順、データ構造、インターフェース。単体で実装できる粒度で>

### 完了条件の確認手段
1. <上の完了条件 1 番目の確認手段>

### 調査記録
<技術調査の結果と出典>

### 参考
<関連する issue やファイル。パス+一言>
```

担当と空の節: create は要約・目的・現状（必要なら決めたこと・未決）だけを書く。polish 担当の節をプレースホルダで置かない。「設計方針」の無い issue は未 polish と読む。決めたこと、未決、調査記録、参考は任意で、書くことが無ければ節を置かない。担当をテンプレートの見出しに書き込まない。 <!-- 担当ラベルはプロセス管理のメタ情報で、issue の読者にはノイズ。issue/2026/07/1518-template-readability.md の判断 -->

折り目: `## 実装メモ` より下は実装者向けで、ユーザーは読まなくてよい。見出しの直下に前置きは要らない。`## 実装メモ` より上は 1 画面（目安 50 行）に収める。超えるなら要約度を上げる。意図が複数なら分割する。

決めたこと: 理由がユーザーの発言にしかない決定だけを書く。コードや技術から理由が導ける決定は設計方針にだけ書く。1 決定 1 行で「決定（理由の要点）」と書き、ユーザーが理由を述べていなければ理由は書かない。日付は書かない（git にある）。応答の記録（「肯定した」「OK と回答した」）は書かない。理由はユーザーの語彙で書き、別の理由（リスク回避、安全側といった聞こえの良いもの）へ言い換えない。設計方針はここに書いた決定と矛盾してはならない。 <!-- 言い換え禁止は issue/2026/07/2700-record-reasons-verbatim.md の判断。議事録化を避けるため人間の判断が入った点だけに絞った。issue/2026/09/1413 -->

未決: ユーザーの判断待ちの論点だけを置く。懸念は、事実なら現状へ、判断なら設計方針の対象外へ書き、どちらでもなければ書かない。空なら節を置かない。 <!-- 旧「リスク・未解決」が懸念と感想の置き場になったための規則 -->

完了条件: 条件だけを書く。確認手段は実装メモの「完了条件の確認手段」に同じ番号で書く。完了条件と確認手段は実装に必要なので、簡潔さのために削らない。ボックスは実装した者が確認手段を実行して埋め、done を呼ぶ前に全て埋まった状態にする。

参照の書式: issue や過去の記録への参照は、本文のどこでも「パス+一言（何の記録か）」で書く。 <!-- 旧命名の数値コードはファイル名と一致しなくなり解読が要った -->

後で読む人に価値のある情報を残し、生成時にしか要らない足場を溜めない。

- 残す: 採用案とその理由、却下した代替案とその理由、後で効く制約（重要な型 / 状態遷移 / プロトコル、試験実装で判明した制約）、既存設計の理解に要る代表的な入口ファイル。
- 溜めない: スキルやコードの手順の丸写し（実体はそちらにあり二重管理で古くなる）、広範なファイルパス列挙、セッションの経緯、他節と重複する記述。

## 良い issue の基準

判定軸は三段に分かれる。

- create の出口: 問題が正しく立っていること（問題の妥当性の4観点を満たす）。
- polish の出口: この issue 単体で実装に着手できること。未決が空であること。
- done の出口: 完了条件が全て埋まり、未決が空で、本文が実態と一致していること。

done を呼ぶ前に、実装者が設計方針と実装メモを実態に合わせて書き換える。残作業は別 issue に切るか捨てる。 <!-- 「計画から外れた点」「積み残し」を追記する案はユーザーが却下（役に立つ場面が思い当たらない）。issue/2026/09/1413 の判断 -->

曖昧語や未確定事項を本文に残さない。
