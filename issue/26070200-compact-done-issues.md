# 完了 issue が計画スキャフォールドを抱えて腐る問題を解く

## 背景・目的
coff の issue は設計判断の長期記憶である。
だが実装が済んだ後も、issue は計画時のスキャフォールド（受け入れ条件・テスト方針・実装手順・セッション経緯など）を抱えたまま残り、後で読む記録としては劣化する。
本 issue の目的は、完了した issue が「後で読んで設計判断だけを与える最小の記録」になる仕組みを立てることである。

なぜ今これを問題とみなすか（妥当性）。
本セッションで作った2つの issue（`26062822`, `26063023`）が 154 行・120 行に膨れ、完了後に手作業で 34 行・28 行へ圧縮する必要が生じた。
膨張の中身は、(a) polish が解決空間を詰めるときに実装手順やコード・ファイルパスを丸写しし（実体はスキル側にあるので二重管理で腐る）、(b) 完了後に済んだ計画部分を落とす規律が無いこと、の2点だった。
`coff-detail-issue` は「実装詳細はすぐ古くなる詳細を書きすぎない」と戒めているが、実際には徹底されず、かつ完了後の圧縮は対象外。
よってこれは実在する問題であり、既存の仕組みでは解決していない。

## 現状
- issue は問題空間を `coff-issue-create`、解決空間を `coff-issue-polish` が書く。完了表記は `coff-issue-done` が `status: done` を付ける（`26063023` で実装）。
- どのスキルにも「完了時に issue を圧縮する」段は無い。done は `status` を変えるだけで本文に触らない。
- polish の実装詳細・自己レビューは「書きすぎない」を detail の注意書きに委ねるのみで、具体的な抑制（スキル手順の丸写し禁止、腐るファイル列挙の抑制）は手順に無い。
- 今回の手作業では、完了 issue を「背景／決めたこと（採用案＋理由）／却下した代替案と理由／参考」の最小構成へ畳んだ。これが妥当な到達形かは未検証（解決空間で検討する）。

## リスク・未解決
- これは2つの別問題の可能性がある。(1) polish の書きすぎ（生成時の抑制）、(2) 完了時の圧縮欠如（状態遷移時の畳み込み）。1 issue にまとめるか分けるかは polish の調査で判断する。
- 圧縮を誰がやるか。`coff-issue-done` に畳み込みを持たせるか、polish/detail に規律として置くか、自動化するか手順に留めるかは解決空間の論点。
- 完了 issue の「あるべき形」を正典化するか。今回採った4節構成をテンプレート化して固定するか、緩いガイドに留めるか。固定は柔軟性を、緩さは再現性を損なう恐れがある。
- 圧縮で情報を失う懸念。却下した代替案とその理由（長期記憶として最も価値がある部分）まで削らないよう、残す/捨てるの線引きを解決空間で定義する。
