# issue ワークフローの役割分担と品質を見直す

## 背景・目的
coff の issue は実装の指示書であると同時に、設計判断の長期記憶でもある。
その issue を作る仕組みが coff-issue-create / coff-issue-polish / coff-detail-issue の3つだが、これらが期待どおり働いていない。
本 issue の目的は、issue ワークフローの役割分担を「問題を立てる」段と「解を詰める」段に切り直し、あわせて polish 段の精度を上げることである。

なぜ今これを問題とみなすか（妥当性）。
本セッションで、create がいきなり解決策まで書き込み、問題が妥当かを検証しないまま issue を作る挙動が実際に出た。
現行スキルには「問題を立てる」と「解を詰める」を分ける軸も、問題の妥当性を吟味する段も存在しない。
よってこれは実在する問題であり、すでに解決済みでもない。

本 issue のスコープは (a) create/polish/detail の役割分担の再設計と、(b) polish 精度の具体化・改善の2点とする。
(b) の主軸は、polish に「本来ユーザーが決めるべき判断は確定前に聞く」段を入れることとし、その型として既存の grilling skill を取り込んで使う。
issue の完了（done）を表す仕組みは独立性が高いため、本 issue には含めず別 issue とする（リスク・未解決を参照）。

## 現状
現行定義（事実）:
- create は「ユーザーの依頼から書ける範囲を埋め、残りは placeholder」とされ、コード調査はしないと定義されている（`.coff/src/coff-issue-create.skill.md`）。
- polish は「コード調査・前提検証・（必要なら）試験実装・多視点レビューで、単体実装できる自己完結 spec に磨く」とされている（`.coff/src/coff-issue-polish.skill.md`）。
- detail はテンプレートと品質基準の唯一の参照元（`.coff/src/coff-detail-issue.skill.md`）。テンプレートは 背景・目的／現状／変更方針／実装詳細／受け入れ条件 などを持つ。
- これら3スキルを参照する他ファイルは無い（`grep` で確認）。変更は3ソースとその compile 成果物に閉じる。

観測した症状:
- create と polish の違いが「完成度の差（素描 vs 調査済み）」で定義されており、「何を書くべきか」の差になっていない。
- その結果、create が解決策（変更方針・実装詳細・受け入れ条件）まで書き込みやすい。実際、本セッションで create した issue は解を含みすぎていた。
- create にも polish にも「問題の妥当性（本当に解くべき問題か・問いの立て方は適切か・別の捉え方はないか）」を検証する段がない。
- polish の精度に不安がある。現行 polish には、本来ユーザーが決めるべき判断を確定前に聞く段が無い。判断を黙って決め打ちするか、リスク・未解決へ送るかしかなく、その結果、推測を仕様として固定してしまう（本セッションでも、ユーザーが指定していない polish の不満内容を、私の診断で勝手に書き込む事象が起きた）。
- あわせて、現行 polish は自己レビュー（手順6）が「多視点で数回」と曖昧で検証可能な観点に紐づかず、採用案に対する代替案と却下理由を記録する要求も無い。設計判断の根拠（＝長期記憶として最も価値のある部分）が残らない。

## 変更方針
役割分担の軸を「完成度の差」から「問題空間 vs 解決空間」へ切り直す。
3スキルを協調して書き換える。

採用案:
- detail を共通の土台にする。テンプレート各節に担当（問題／解／横断）のラベルを付け、品質基準を create の出口と polish の出口の二段に分け、「問題の妥当性」の観点を定義して両スキルから参照させる。
- create は「問題を立てる」段に限定する。問題空間（背景・目的／現状）だけを書き、問題の妥当性を吟味し、解決空間は書かない。
- polish は「解を詰める」段として明確化する。入口で問題空間を点検し（崩れていれば問題空間へ差し戻す）、コード調査で解決空間を実装可能な粒度まで埋める。
- (b) の主軸として、polish に「judgment call を確定前にユーザーへ聞く」段を入れる。その型は grilling skill（Matt Pocock、MIT）を vendoring して使う。grilling の規律は「一度に1問・各問に推奨回答を添える・コードで分かることは聞かずに調べる」。最後の規律は本件の問題空間／解決空間の線引きと一致する（コードで答えが出る前提検証は polish が調べ、本当にユーザーの判断なものだけ聞く）。
- 補助的な精度対策として、代替案と却下理由の記録を必須にし、自己レビューを具体的なチェックリストにする。これらは redesign を広げず、チェックリスト項目として軽く拾う。

検討した代替案と却下理由（設計判断の記録）:
- 代替1: スキルの役割はそのままで、テンプレートや detail を厚くするだけにする。→ create/polish の役割の混線そのものは直らないので不十分。却下。
- 代替2: create を廃し polish 一本にする。→ 「問題を軽く立てる」入口と、そこでの妥当性検証を失う。issue が設計の長期記憶である以上、問題の立て方を独立した段として残す価値が高い。却下。
- 代替3（(b) の実現方法）: grilling の原理を polish ソースへ内蔵し、外部 skill は取り込まない。→ 数行で済み自己完結する利点はあるが、grilling を尋問の汎用部品として create や設計時にも再利用したいため、vendoring（採用案）を選ぶ。配布先で参照が切れないよう、名前だけ参照ではなく実体を同梱する。

## 実装詳細
ソースは日本語で編集し、`/coff-compile coff-detail-issue coff-issue-create coff-issue-polish` で成果物を再生成する。
成果物は直接編集しない（compile が日本語→英語訳・コメント除去・md5 フッタ付与を行う）。

### coff-detail-issue（共通の土台）
1. テンプレートの各セクション見出しに担当ラベルを付す。
   - 〔問題 / create が立てる〕背景・目的、現状
   - 〔解 / polish が詰める〕変更方針、対象範囲・対象ファイル、実装詳細、受け入れ条件、テスト方針
   - 〔横断〕人間が決めた判断、リスク・未解決、参考・関連 issue
2. 「良い issue の基準」を二段に分ける。
   - create の出口: 問題が正しく立っていること。
   - polish の出口: この issue 単体で実装に着手できること（現行基準）。
3. 「問題の妥当性」の観点を定義して置く（共通参照元なので両スキルがここを参照する）。
   - 本当に解くべき問題か / すでに解決していないか / 問いの立て方は適切か / 別の捉え方はないか。
4. 実装詳細の粒度に注意書きを足す。すぐ腐る詳細（広範なファイルパス列挙・コード片）を書きすぎない。ただし既存設計の理解に要る代表的な入口ファイル、重要な型／状態遷移／プロトコル、spike で判明した制約は書いてよい。
5. テンプレートに「人間が決めた判断」セクション（横断）を新設する。AI が勝手に決めた箇所と人間が決めた箇所の境界を本文に残すためのもの。各項目は「決定内容／理由／（未確定なら）要確認の旨」を持つ軽量な形式とする。リスク・未解決（要判断の置き場）や変更方針の代替案記録とは役割が異なる（こちらは確定済みの判断の provenance を残す）。

### coff-issue-create（問題を立てる）
手順を次に置き換える。
1. detail を読み、保存先・命名・テンプレート・品質基準を把握する。
2. `issue/` が無ければ作成する。
3. 問題空間だけを書く。ユーザーの依頼から 背景・目的 と 現状（問題の所在）を言語化する。
4. 問題の妥当性を吟味する（detail の4観点）。疑い・別の捉え方・棄却した枠は「リスク・未解決」に落とす。深いコード調査はしない（問題の存在確認に最小限読むのは可）。
5. 解決空間（変更方針・対象範囲・実装詳細・受け入れ条件・テスト方針）は書かない。「解決空間。polish で詰める」等のプレースホルダを置く。
6. 採番してファイルを作成し、パスを報告する。polish を案内する。
- 出口基準: 問題が正しく立っていること。

### coff-issue-polish（解を詰める）
手順を次に置き換える。現行の試験実装の安全手順は維持する。
1. detail を読み、テンプレートと品質基準を把握する。
2. 対象 issue を読み、まず問題空間を点検する。妥当性4観点を満たし問題が正しく立っているか確認し、崩れていれば 背景・目的／現状 を立て直す（問題空間への差し戻し）。
3. コード調査。関連ファイル・既存実装・依存を実際に読み、現状（事実）／対象範囲／実装詳細 を埋める。
4. 前提検証をチェックリストで行う。記載の前提が現コードと矛盾しないか / 参照するファイルパスが実在するか / 受け入れ条件が検証可能か。矛盾は修正し、要判断は「リスク・未解決」へ移す。
5. judgment call の仕分け。詰める過程で出る論点を「コードで答えが出る」「ユーザーの判断が要る」に分ける。前者は手順3-4（関連コード・既存 skill・docs・関連 issue を読む）で自分で解決し、人間には聞かない。後者だけ grilling skill の規律で確定前に聞く（一度に1問・各問に推奨回答を添える）。grilling ループの出口は「汎用的な合意」ではなく「この issue が単体で実装可能になること」に固定する。聞いた結果と決定は本文に反映し、人間が決めた判断は「人間が決めた判断」セクションに記録する。決め打ちで仕様化しない。
6. 解決空間を詰める。変更方針には採用案に加え、検討した代替案と却下理由を必ず記録する（設計判断の長期記憶のため）。受け入れ条件とテスト方針も埋める。
7. （必要なら）試験実装。安全手順は現行どおり（`git stash` 退避、別プロセスは codex-delegate に委譲、issue 追記以外はコミットしない）。
8. 自己レビューを具体チェックリストで行う。テンプレ各節が埋まっているか / 受け入れ条件は検証可能か / テスト方針は十分か / 前提とコードが一致するか / リスクを網羅したか / ユーザーに聞くべき judgment call を黙って決め打ちしていないか / 実装者が迷う箇所はないか。
9. issue を上書きし、適用した変更点と残課題を報告する。
- 出口基準: 実装者が issue 単体で着手できること（現行基準）。

### grilling の vendoring
japanese-tech-writing と同じ vendored 方式で取り込む（`.coff/src/` にソースを置かず、coff-compile の対象外、md5 フッタも付けない）。
1. 取り込み。`gh skill install mattpocock/skills grilling --agent claude-code` を試す（要 gh ≥ v2.90.0）。grilling は `skills/productivity/grilling` と深くネストするため、ベース名 `grilling` で解決しなければ、`skills/productivity/grilling/SKILL.md` を `.claude/skills/grilling/SKILL.md` へ手でコピーするフォールバックを採る。
2. MIT 帰属の保全。`.claude/skills/grilling/` に MIT のライセンス全文と著作権表示（`Copyright (c) 2026 Matt Pocock`）を同梱する。`gh skill install` が LICENSE を運ばない場合は手で `LICENSE` を置く。coff は再配布されるため、notice が coff と一緒に旅する状態を必須とする。
3. polish（必要なら create）から grilling を名前で参照する。実体が同梱されているので、配布先でも参照が切れない。

## 受け入れ条件
- [ ] detail のテンプレート各節に担当ラベル（問題／解／横断）が付いている
- [ ] detail の品質基準が create 出口（問題が正しく立つ）と polish 出口（実装着手可）の二段になっている
- [ ] detail に「問題の妥当性」の4観点が定義され、共通参照元として置かれている
- [ ] detail のテンプレートに「人間が決めた判断」セクション（横断）が新設され、polish がそこへ人間判断を記録する手順になっている
- [ ] detail に「実装詳細は腐りやすい詳細を書きすぎない」注意書きがある
- [ ] create の手順が問題空間のみを書くものになり、解決空間はプレースホルダにする旨が明記されている
- [ ] create に問題の妥当性を吟味するステップがある
- [ ] polish の入口に問題空間の点検と差し戻しがある
- [ ] polish に judgment call の仕分け（コードで調べる／ユーザーに聞く）の段があり、後者で grilling の規律に従う
- [ ] polish の変更方針に「代替案と却下理由を記録する」要求がある
- [ ] polish の自己レビューが具体チェックリストになっている（「聞くべき判断を決め打ちしていないか」を含む）
- [ ] grilling が `.claude/skills/grilling/` に原文で vendoring され、MIT の著作権表示とライセンス全文が同梱されている
- [ ] grilling が coff-compile の対象外（`.coff/src/` に対応ソースが無く、md5 フッタも付かない）
- [ ] 3ソースを編集し `/coff-compile` で成果物が再生成されている（成果物を手で編集していない）
- [x] issue 完了表記(c) は本 issue の対象外で、別 issue として起票されている（`issue/26063023-issue-done-status.md`）

## テスト方針
ドッグフードで検証する。
- create を1回かけ、新規 issue が問題空間だけを持ち（解決空間が placeholder）、妥当性を吟味した跡があることを確認する。
- 同じ issue を polish にかけ、解決空間が埋まり、変更方針に代替案と却下理由が記録されることを確認する。あわせて、ユーザー判断が要る論点で grilling 規律（一度に1問・推奨つき）に沿って聞けることを確認する。
- grilling が skill 一覧にロードされ、`.claude/skills/grilling/` に MIT の notice が同梱されていることを確認する。
- `/coff-compile coff-detail-issue coff-issue-create coff-issue-polish` を実行し、3件が `compiled` になり、成果物の本文が意図どおり変わることを確認する。あわせて、引数なしの `/coff-compile` で grilling が処理対象に出ないことを確認する。
- 既存 issue（本 issue 自身、`issue/26062803-import-tech-write-ja.md`）が、新しいテンプレート・ラベルと矛盾しないことを目視する（節は増減しないので影響は小さい想定）。

## 人間が決めた判断
本 issue を grilling で詰める過程で、ユーザーが決めた判断とその理由を残す（新設セクションのドッグフード）。
- [x] 役割分担を「問題空間／解決空間」で切り直す（B を採用）。理由: 「完成度の差」での区別が、create が解に飛ぶ原因だった。
- [x] create は軽く grill、polish は本格的に grill。理由: create を軽量・高速に保ち、「軽く立てて polish で詰める」入口の性質を守るため。
- [x] (b) は grilling を vendoring して実装（原理内蔵案は却下）。理由: 汎用の尋問部品として再利用したい／配布先で参照が切れないよう実体を同梱する。
- [x] GPT Pro 提案の周辺スキル（split-issue 等）は本 issue では不採用。理由: 1 issue = 1 問題を守る。有用なものは将来別 issue。
- [x] 「人間が決めた判断」セクションをテンプレートに新設。理由: polish が強くなるほど AI/人間の判断境界が曖昧になるため、provenance を本文に残す。
- [x] (c) 完了表記を別 issue に切り出す。理由: 完了表記は独立性が高い。→ `issue/26063023-issue-done-status.md` を起票済み。
- [x] 既存 issue へ新基準を遡及しない（新規から適用）。理由: 遡及は手間のわりに価値が薄く、既存記録を壊すリスクがある。必要な issue は次の polish で自然に新形式へ寄せる。

## リスク・未解決
- (c) issue 完了表記の欠如は別 issue として切り出す。本 issue とスコープを混ぜない。完了は削除ではなく状態遷移で表すべき（issue は長期記憶のため）という論点を、その issue の問題空間で立て直す。
- (b) の「精度の低さ」の中身は、ユーザーがまだ言語化しきれていない。本 issue では grilling 流の「聞く段」を主軸に据え、他の弱点（コード調査の浅さ等）はチェックリスト項目で軽く拾うに留めた。運用で弱点が顕在化したら追補する。
- create も grilling すべきかは未確定。既定は polish 主体とし、create は問題の框が曖昧なときだけ軽く聞く。create を重くしすぎない。要判断。
- MIT 帰属義務。grilling を vendoring・再配布する以上、著作権表示とライセンス全文を必ず同梱する。`gh skill install` が LICENSE を運ぶかは取り込み時に確認し、運ばなければ手で置く。
- gh のバージョン依存。`gh skill` は v2.90.0+ が必要（取り込み・更新時のみ）。深いネスト（`skills/productivity/grilling`）が `gh skill` で解決しなければ手コピーにフォールバックする。
- 既存 issue への遡及。担当ラベルや新基準の適用は新規 issue からとし、過去 issue は触らない方針を推奨する。要判断。
- 別の捉え方の残余。問題がスキルの役割分担ではなくテンプレート/detail の薄さに起因する可能性は、代替1として検討し却下した。テンプレートの厚みは detail の改修で部分的に手当てする。
- GPT Pro が提案した周辺スキル（`split-issue` / `issue-ready-check` / `to-issues` / `grill-with-docs`、docs・ADR の自動更新、人間質問の上限予算）は、本 issue のスコープ（create/polish/detail ＋ grilling）を越えるため本 issue では採用しない。有用なものは将来別 issue として検討する（1 issue = 1 問題を守る）。
