# polish の書きすぎを抑え、issue を長期記憶として保つ

## 背景・目的
coff の issue は設計判断の長期記憶である。
だが polish が解決空間を詰めるとき、後で読む人には不要ですぐ古くなる情報まで書き込みやすい。
その結果 issue が膨張し、記録としての価値が下がる。
本 issue の目的は、polish が生成時に書きすぎないようにして、issue を後で読んで価値のある設計判断だけの記録に保つことである。

なぜ今これを問題とみなすか（妥当性）。
本セッションで作った2つの issue（`26062822`, `26063023`）が 154 行・120 行に膨れ、完了後に手作業で 34 行・28 行へ畳む必要が生じた。
落とした中身の大半は、実装手順やコードの丸写し（実体はスキル側にあり二重管理で古くなる）、すぐ古くなるファイルパス列挙、セッションの経緯、重複したリスク記述だった。
これらはいずれも「生成時に書かなければよかった」もので、下流で畳むより polish で抑えるのが本筋である。
`coff-detail-issue` は「実装詳細はすぐ古くなる詳細を書きすぎない」と既に戒めているが、この一箇所に留まり徹底されていない。
よってこれは実在する問題であり、既存の仕組みでは解決していない。

## 現状
- 解決空間は `coff-issue-polish` が詰める。手順6で変更方針や実装詳細を埋め、手順8でチェックリスト自己レビューを行う。
- `coff-detail-issue` は「実装詳細」節にだけ「すぐ古くなる詳細を書きすぎない」注意書きを持つ。ただし何を残し何を溜めないかの基準としては弱い。
- polish の自己レビュー観点に「後で読む人に無用な情報を書いていないか」は無い。
- 完了状態は `coff-issue-done` が `status` を切り替えるだけで本文に触らない（`26063023` で実装）。この保証は保つ。

## 変更方針
根っこは polish の生成時の書きすぎである。
下流に畳み込み操作を新設せず、生成時に抑える。

- `coff-issue-polish` に、書きすぎを抑える指示を足す。
  - 実装詳細に、スキルやコードの手順を丸写しせず参照で済ませる。すぐ古くなるファイルパス列挙をしない。
  - 自己レビューのチェックリストに「後で読む人に無用な、またはすぐ古くなる情報を書いていないか」を加える。
- `coff-detail-issue` の「書きすぎない」注意書きを基準へ格上げする。
  issue は長期記憶であり、後で読む人に価値のある設計判断（採用案、却下案とその理由）を残し、生成時にしか要らない足場を溜めない、と明示する。
- 受け入れ条件とテスト方針は残す。実装に必要なので消さない。

検討した代替案と却下理由:
- 圧縮専用スキルを新設し、完了時に本文を畳む。→ 根っこは書きすぎで、畳み込みは下流の掃除にすぎない。書きすぎなければ畳む対象は小さい。操作を増やすより生成時に直すほうが本質的。
- `coff-issue-done` に圧縮を乗せる。→ done の「本文を変えない」保証（安全で予測可能）を壊し、状態フラグの操作に非可逆な書き換えが混ざる。
- 「書きすぎ抑制」と「完了時の圧縮」を別 issue に割る。→ 完了時に古びて見えたのは書きすぎの症状であって独立の問題ではない。1つの問題として扱う。

## 実装詳細
- detail: 「実装詳細」節の注意書きを、issue 全体にかかる基準へ言い換える。
  残すもの（設計判断＝採用案、却下案とその理由、後で効く制約）と、溜めないもの（スキルやコードの手順の丸写し、広範なファイルパス列挙、セッションの経緯、重複記述）を対比で示す。
- polish: 手順6（解決空間を詰める）に「丸写しせず参照で済ませる／すぐ古くなる列挙をしない」を足し、手順8の自己レビューに上記の観点を1項目加える。
