# issue に完了（done）を表す仕組みを追加する

## 背景・目的
issue を作った後、それが完了したことを表す手段が今は無い。
coff の issue は実装の指示書であると同時に、設計判断の長期記憶でもある。
だからこそ、完了したものを単に消すのではなく、完了したと明示したうえで記録として残せる必要がある。
本 issue の目的は、issue の完了をどう表現するかという問題を立てることである。

なぜ今これを問題とみなすか（妥当性）。
完了に近い既存要素は「受け入れ条件」のチェックリストだけで、これは個別条件の達成を表すもの。
issue 全体の状態（着手前／進行中／完了など）を表す欄は存在しない。
よってこれは実在する問題であり、すでに解決済みでもない。

解き方（状態欄を足す／別ディレクトリへ移す等）は本 issue では決めない。
表現方法の設計は polish に委ねる。

## 現状
- issue は `issue/<yymmddHH>-<slug>.md` の Markdown ファイル（1 issue = 1 ファイル、`coff-detail-issue` 参照）。
- issue 本文は `# <タイトル>` から始まり、YAML frontmatter を持たない。
- 完了・未完了を一覧で見分ける手段、完了日を記録する場所、完了したものを区別して保管する仕組みのいずれも無い。
- 完了に最も近いのは「受け入れ条件」のチェックリストだが、これは個別条件の達成であって issue 全体の状態ではない。
- issue 同士はファイルパスで相互参照しうる（「参考・関連 issue」）。完了時に保管場所を変える設計を採るなら、この参照の扱いが論点になる。

## リスク・未解決
- 問いの立て方の幅。「完了をどう表すか」は、(1) 状態をどこに書くか、(2) 完了したものを保管場所で区別するか、(3) 機械処理（一覧・集計）を要するか、で枝分かれする。どれを主たる問題に据えるかは polish の調査で絞る。
- 別の捉え方。本当の必要は「完了表記」そのものではなく、「進行中の issue と完了済みの設計記録を一覧で見分けること」かもしれない。この再framing も polish で検討する。
- 長期記憶としての価値。完了だけでなく「却下した設計とその理由」を残せると価値が高い、という観点もある。状態の値域に含めるかは未確定。
