# done の前に検証のボックスを実装した者が埋める

## 要約
done 済み issue の検証チェックボックスが未チェックのまま残り、記録が「未達のまま完了」に見える。
実装した者が確認手段を実行してボックスを埋めてから done を呼ぶ規則を detail に足し、done ゲートは全ボックスが埋まっているかを確認するよう改める。

## 背景・目的
done 済み issue の検証（旧テンプレートでは受け入れ条件）のボックスが `- [ ]` のまま残り、後から読むと条件未達のまま完了したように見える。
原因は、誰がいつボックスを埋めるかが決まっていないことにある。
記録を事実と一致させる。

## 現状
- `issue/2026/07/0200-polish-write-restraint.md` と `issue/2026/07/0222-issue-upkeep-and-cleanup.md` は `status: done` だが、受け入れ条件のボックスは全て未チェックである。
- done ゲートは各項目の充足を確認するが、ボックスには触れない（本文を変えない原則）。
- 検証の新形式（条件と確認手段の併記）は導入済みで、確認手段を実行すればボックスは機械的に埋められる。

## 変更方針
実装した者が、検証の各条件の確認手段を実行してボックスを埋めてから done を呼ぶ。
done ゲートは「全ボックスが埋まっているか」を確認し、未チェックがあれば保留する。

検討した代替案と却下理由。

- done ゲートがボックスを埋める。done の「本文を変えない」原則（`issue/2026/06/3023-issue-done-status.md` の判断）を破るため却下。
- 埋めずに読み方だけを文書化する。「`status: done` はゲート通過を意味する」という間接的な読解を読者に強いる。確認手段の実行と同時に埋めれば手間は小さいので却下。
- 過去の done issue のボックスを遡及して埋める。過去 issue の修正は今後楽になるものだけ、という運用方針によりスコープ外。

## 実装詳細
- `.coff/src/coff-detail-issue.skill.md` のテンプレート節末尾の散文（「ただし検証（完了の条件と確認手段）は実装に必要なので、簡潔さのために削らない。」の直後）に、ボックスは実装した者が確認手段を実行して埋め、done を呼ぶ前に全て埋まった状態にする旨を1文足す。テンプレートのコードブロックは変えない。
- `.coff/src/coff-issue-done.skill.md` の手順3の1点目を、全ボックスがチェック済みかの確認に置き換える。条件の内容が実際に満たされているかの実質確認は、既存2点目の本文と実リポジトリの整合確認が引き続き担う。
- 旧テンプレートの「受け入れ条件」節にも同じ規則を適用する。done の手順3にある既存の括弧書き（旧テンプレートでは「受け入れ条件」節）を維持すれば足り、detail 側への追記は不要。
- `/coff-compile` で反映する。

## リスク・未解決
- 虚偽チェック（確認手段を実行せずに埋める）は防げない。done ゲートの整合確認で明らかな食い違いだけを拾う。
- 実装者シミュレーションで残った指摘: 検証の条件2は成果物の記述の静的確認にとどまり、ゲートの振る舞いそのものは未チェック issue への done 試行でしか確かめられない。振る舞いの確認は運用初回の done で兼ねる。
