# issue テンプレートと文章の読みコストを下げる

## 背景・目的  〔問題 / create〕
人間が issue を読むコストが高い。
原因は構造と文体の両方にある。

構造面では、テンプレートが同じ情報の再掲を誘発している。
同じ決定が変更方針、人間が決めた判断、リスク・未解決の3節に現れ、読者は同じ内容を読み比べることになる。
冒頭に要約がなく、何をする issue か知るまでに20行以上かかる。
受け入れ条件とテスト方針がほぼ言い換えになる。
見出しの担当ラベル〔問題 / create〕はプロセス管理のメタ情報で、読むたびに視界に入る。
issue 間の参照が旧命名の数値コードで書かれ、現在のファイル名と一致せず解読が要る。

文体面では、スラッシュと入れ子括弧で節を詰め込む書き方が一読で解けない。
japanese-tech-writing 規範は issue 本文の適用対象なのに、徹底されていない。

冒頭要約の新設、節統合、担当ラベルの扱い、参照書式、文体規範の徹底を、一体のテンプレート改訂として見直す。

## 現状  〔問題 / create〕
- coff-detail-issue のテンプレートは10節と担当ラベルからなり、要約節はない。
- 重複の実例: `issue/2026/07/0222-issue-upkeep-and-cleanup.md` では、done 軽量ゲートの決定が変更方針（27-33行）、テスト方針（74行）、人間が決めた判断（80行）に現れる。
- 要約不在の実例: 同 0222 は変更内容に到達するまで22行。`issue/2026/07/0200-polish-write-restraint.md` は妥当性論証の段落（12-17行）が変更方針より先に来る。
- 言い換えの実例: 0222 の受け入れ条件（63-71行）とテスト方針（73-76行）は同じ内容の名詞形と動詞形である。
- 参照の実例: 0200 の13行と62行は `26062822` 形式の旧数値コードで参照する。年月階層化でファイル名から年月が落ち、このコードは実ファイル名と一致しなくなった。
- 対比: 手作業で圧縮済みの done issue 2件（`issue/2026/06/2822-improve-issue-workflow.md`、`issue/2026/06/3023-issue-done-status.md`）は、短い背景の直後に「決めたこと」が来る構成で読みやすい。
- 文体の実例: 0222 の33行「受け入れ条件の確認のみ（現状との食い違い検出を失う。ユーザーが軽量ゲートを選択）」のような詰め込みが多用される。

## 変更方針  〔解 / polish〕
テンプレートを次の9節構成に改訂する（ユーザーがプレビューを承認済み）。

```markdown
# <タイトル>

## 要約
<2、3行: 何をなぜどう変えるか。polish が最後に書く>

## 背景・目的
## 現状
## 変更方針
<採用案と却下案をここに集約する。却下案を他節に書かない>

## 実装詳細
<対象範囲・対象ファイルを含む>

## 検証
- [ ] <条件> — 確認: <手段>

## 人間が決めた判断
<由来のみ。決定の実体は変更方針に書き、ここには何を人間が決めたかと理由の要点、日付だけを残す>

## リスク・未解決
## 参考・関連 issue
```

あわせて次を定める。

- 担当ラベルは issue 生成物の見出しに書かない。どのスキルがどの節を書くかは detail のテンプレート説明の地の文にだけ残す。
- 参照書式。issue や過去の記録への参照は、裸の数値コードでなく「パス+一言（何の記録か）」で書く。
- 文体。polish の自己レビューに japanese-tech-writing 準拠の観点を明示し、スラッシュや入れ子括弧で詰め込んだ文を残さない。

検討した代替案と却下理由。

- 統合せず、重複は書き手の規律で抑える。0222 で規律が節構成に負けた実証があるため却下。
- 検証統合（受け入れ条件+テスト方針）だけ行う。重複の主因である却下案の3節分散が残るため却下。
- done 転換時に文書の形を変える案（圧縮、最小完了記録、ライフサイクル別テンプレート）。先行議論で見送り済み。今回は生成時の形だけを変える。

## 対象範囲・対象ファイル  〔解 / polish〕

- `.coff/src/coff-issue-create.skill.md`（プレースホルダで残す節の対応）
- `.coff/src/coff-issue-polish.skill.md`（要約を書く手順、検証節の形式、自己レビューの文体観点）
- `.coff/src/coff-issue-done.skill.md`（チェックリストを読む節名の変更）
- `/coff-compile` で反映する

## 実装詳細  〔解 / polish〕
- detail のテンプレートを差し替え、担当（問題空間は create、解決空間と要約は polish、横断は両方）はテンプレートの外の地の文で説明する。
- create は要約、変更方針、実装詳細、検証をプレースホルダで残す。
- polish の手順に「最後に要約を書く」を足す。検証節は各条件に確認手段を併記する形式とする。
- done は「検証」節のチェックリストを読むよう文言を直す。旧テンプレの issue も done にできるよう、旧節名「受け入れ条件」も許容する。
- 既存 issue は変換しない。

## 受け入れ条件  〔解 / polish〕
- [x] detail のテンプレートが9節構成で、生成物の見出しに担当ラベルがない
- [x] 検証節の形式（条件と確認手段の併記）が定義されている
- [x] 参照書式（パス+一言。裸の数値コード禁止）が定義されている
- [x] polish の自己レビューに文体観点（japanese-tech-writing 準拠、詰め込み文体の禁止）がある
- [x] create / polish / done が新しい節名と整合し、done は旧節名「受け入れ条件」も読める
- [x] 既存 issue が変更されていない
- [x] `/coff-compile` で成果物に反映されている

## テスト方針  〔解 / polish〕
- 新テンプレートで issue を1本 create から polish まで通し、要約が冒頭に来ること、却下案が変更方針の外に現れないこと、検証節が条件+手段の形になることを確認する。
- 旧テンプレートの open issue（本 issue 群）を done にする際、done ゲートが旧節名を読めることを確認する。

- 担当ラベルは生成物から除去する（2026-07-16）。
- 要約、節統合、ラベル、参照書式、文体徹底を1 issue に統合し、1問題ゲートは別 issue に分離する（2026-07-15、codex の勧告をユーザーが承認）。

## リスク・未解決  〔横断〕
- 新旧テンプレートの混在期間ができる。done が両方の節名を許容して吸収する。
- 「人間が決めた判断」を由来のみに薄くすると、決定の中身を探すには変更方針を読む必要がある。polish が変更方針側に決定の主体を書き分けることで補う。
- done 転換時の文書の形は見送り。本改訂後も done issue の読みにくさが残れば別 issue で扱う。
