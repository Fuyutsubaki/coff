# done 後の issue から実装への辿り方を定める

## 背景・目的  〔問題 / create〕
issue は done になった後も設計判断の記録として読まれるが、いつ、どの変更で完了したのかを知る手順が定まっていない。
完了の文脈（完了日時、実装の所在）に issue から到達できるようにする。

## 現状  〔問題 / create〕
- coff-issue-done は軽量ゲートを通したあと frontmatter の `status` を `done` に書き換えるだけで、完了の文脈への辿り方はどこにも書かれていない。
- 実際には git から導出できることを本 polish で検証済みである。issue ファイルの `status` 行を blame すると完了コミットが返り（0200 で `afa8602`、0222 で `29368d5`）、`gh pr list --search <ハッシュ> --state merged` がその PR を返す（`29368d5` から PR #8 に到達）。
- `git log -S 'status: done'` による探索は、本文にその文字列を含む issue で誤検知する（0222 で確認。本文が一覧用の grep コマンド例を含むため）。
- このリポジトリは done への変更と実装を同じ PR に入れて運用している（PR #8 で確認）。

## 変更方針  〔解 / polish〕
frontmatter への記録はしない。
完了の文脈は git から導出でき、記録すると二重管理になるためである。
代わりに coff-detail-issue の状態節に、辿り方を短く明文化する。

- 完了コミットと完了日時は、issue ファイルの `status` 行の blame で特定する。
- 実装は、完了コミットが属するマージ済み PR から辿る。
- 前提として、done への変更と実装は同じ PR に入れる運用を明文化する。これが崩れると PR 経由で実装に辿れなくなる。

検討した代替案と却下理由。

- frontmatter に完了日と実装の所在（PR 番号かブランチ名）を記録する。git から導出できる情報の二重管理になるためユーザーが却下した。コミットハッシュは done 時点で未確定という順序制約もあった。
- 検証要約も frontmatter に残す。同じ理由に加え、frontmatter が肥大化する。
- 本 issue ごと削除する。frontmatter 記録を却下した判断自体が長期記憶に値するため残す。

## 実装詳細  〔解 / polish〕
- 状態節の「完了しても issue ファイルは元の場所に残す」の直後に、辿り方（blame と PR 検索のコマンド例つきで2、3行）と同一 PR 運用の前提を足す。
- `git log -S` 方式は誤検知があるため書かない。

## 人間が決めた判断  〔横断〕
- frontmatter への完了記録はやめ、git での辿り方の明文化に転換する。理由: git から導出できる情報の二重管理を避ける（2026-07-16）。
- 過去 issue の遡及補正（done 済み issue の未チェックボックス解消など）はスコープに含めない。理由: 過去 issue の修正は今後楽になるものだけ、という運用方針（2026-07-15）。frontmatter を欠いていた `issue/2026/06/2803-import-tech-write-ja.md` は本 issue とは別に直接修正済み。

## リスク・未解決  〔横断〕
- 同一 PR 運用が破られると PR 経由の辿りが崩れる。明文化で予防するにとどめ、強制する仕組みは作らない。
- squash マージなどで履歴が書き換わると blame の結果が変わる。現状の運用（マージコミット）では問題ない。
