# issue の目的を明文化し、何を issue にするかの入口基準を定める

## 背景・目的  〔問題 / create〕
coff の issue は実際には三つの役割を担っている。
実装の仕様書、AIと人間の橋渡し、設計判断の長期記憶である。
このうちリポジトリに明文があるのは「設計判断の長期記憶」だけで、「AIと人間の橋渡し」はユーザーの発言にしか存在しない。
目的が暗黙のままだと、issue 体系への変更の是非を評価する物差しがなく、見直しのたびに目的の推定からやり直すことになる。
また、目的が決まれば「何を issue にするか（直接直すか、issue を立てるか）」の入口基準も従属して決まるが、これも未定義である。
issue の目的を一文で定義し、入口基準とあわせて明文化する。

## 現状  〔問題 / create〕
- README は3行で、issue 体系に触れていない。
- coff-detail-issue は「issue は設計判断の長期記憶である」とだけ書く。
- 橋渡しの機能は実装済みである。「人間が決めた判断」節、grilling の規律、polish 手順5の論点仕分け（コードで答えが出るか、人間の判断が要るか）がそれにあたる。ただし目的としての明文はない。
- 「チームの issue」（優先度、担当、期限）を担うための項目はテンプレートにない。

## 変更方針  〔解 / polish〕
`.coff/src/coff-detail-issue.skill.md` に「目的」節を新設し、次の4点を明文化する。

- issue の定義。issue は AI と人間が共有する作業単位の記録であり、open の間は実装契約（実装者が issue だけで着手できる仕様書）、done 後は設計判断の長期記憶として読む。
- 橋渡しの位置づけ。「人間が決めた判断」節と polish の論点仕分けは、AI と人間の判断の境界を本文に残すための仕組みである、と目的を添える。
- 入口基準。すべての変更は issue を通す（チーム開発で PR を通すのと同じ強さの運用）。issue の単位は「1つの意図」であり、PR 並みに粗くてよい。独立に採否を判断できる問題は束ねない。作業中の issue の意図に従属する軽微修正は、その issue に同乗してよい。単独の軽微な変更は、問題空間だけの数行の issue を即立てて即 done にしてよい。
- 担わないもの。チームの issue 管理（優先度、担当、期限）は担わない。

テンプレート下にある「issue は設計判断の長期記憶である」の段落は、新設の目的節と重複しないよう統合する。

検討した代替案と却下理由。

- README への併記。ユーザー判断で detail のみとした。スキルが毎回読む場所に集約する。
- 三役並記の定義（仕様書、橋渡し、長期記憶を対等に並べる）。評価の物差しとしての鋭さが落ちるため、寿命で切る形をユーザーが選んだ。
- 入口基準の二条件案（契約が要るか、記憶に残す判断が出るときだけ issue にする）。ユーザーが却下した。PR を通さない修正を許さないのと同じ程度に、issue を通さない修正も許可しない方針を採る。

## 対象範囲・対象ファイル  〔解 / polish〕
- `.coff/src/coff-detail-issue.skill.md`（目的節の新設、長期記憶段落の統合）
- `/coff-compile` で `.claude/` へ反映する
- create / polish / done の各ソースは変更しない見込み。detail を読む手順が既にあるため、目的節は自動的に届く。実装時に矛盾がないかだけ確認する。

## 実装詳細  〔解 / polish〕
- 目的節は detail の冒頭（「直接呼び出し時の動作」の直後）に置く。以降の節（保存先、状態、テンプレート、品質基準）の前提になるため。
- 文面は変更方針の4点をそのまま書く。コンパイルで英訳されても意味が保たれる平易な文にする。
- 「1つの意図」の説明には、判定に使える対比例を1組だけ添える。表記ゆれの一括修正は多数ファイルに触れても1意図であり、独立に採否を判断できる複数の整備は束ねない、という対比。

## 受け入れ条件  〔解 / polish〕
- [x] detail に目的節があり、open=実装契約、done=設計判断の長期記憶という寿命による定義が書かれている
- [x] 入口基準（全変更 issue 必須、1 issue = 1 意図、独立採否問題の禁止、軽微修正の同乗可）が書かれている
- [x] チームの issue 管理を担わない旨が書かれている
- [x] 長期記憶に関する既存の記述と二重になっていない
- [x] `/coff-compile` で成果物に反映されている

## テスト方針  〔解 / polish〕
- compile 後の成果物を読み、create / polish / done の各手順と矛盾しないことを確認する。
- 次に軽微な修正が発生した場面で、入口基準どおり（数行 issue の即立て即 done、または同乗）に運用できることをドッグフードで確かめる。

## 人間が決めた判断  〔横断〕
- 棄却状態（`rejected`）の導入は見送る。理由: YAGNI。立てたが取り下げた issue の判断が痕跡なく消える問題は認識のうえで、必要が顕在化してから別 issue で扱う（2026-07-15）。
- 目的は寿命で切る形（open=実装契約、done=判断記録）で定義する（2026-07-16）。
- 置き場所は detail のみとし、README には書かない（2026-07-16）。
- 入口基準は「全変更 issue 必須。単位は1意図で PR 並みに粗くてよい。独立採否問題は束ねない。軽微修正の同乗可」とする（2026-07-16）。

## リスク・未解決  〔横断〕
- 一文定義が形骸化する恐れがある。他 issue の評価に実際に使われて初めて意味を持つ。
- 「独立に採否を判断できる」の判定には主観が残る。運用で判断例が溜まったら detail の対比例を増やす。
- 全変更 issue 必須の運用は、issue を経ずに直す従来の習慣が残っていると崩れる。ドッグフード（テスト方針）で定着を確かめる。
