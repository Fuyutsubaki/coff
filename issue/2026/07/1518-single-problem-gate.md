# 1 issue = 1 意図を create と polish で点検する

## 背景・目的  〔問題 / create〕
独立した複数の問題を1つの issue に束ねると、読みと検証のコストが問題数と節数の掛け算で膨らむ。
実例が `issue/2026/07/0222-issue-upkeep-and-cleanup.md` で、独立な3問題（A/B/C）の分岐が10節すべてを貫き、97行の中で1系統を追う読者は9箇所をジャンプすることになる。
issue の粒度の規範は過去 issue の判断記述に現れるだけで、coff-detail-issue に明文がなく、create にも polish にも点検の段がない。
規範にもとづく検査を create と polish に設ける。

## 現状  〔問題 / create〕
- coff-detail-issue には「1 件の issue につき 1 つの Markdown ファイル」の規定はあるが、粒度の規範はない。
- `issue/2026/06/2822-improve-issue-workflow.md` の却下案に「1 issue = 1 問題を守る」という記述があり、これが規範の唯一の痕跡である。
- 0222 はユーザー指示で3問題を束ねた。点検の段がないため、指示があれば原則は抵抗なく破れる。
- 粒度の規範そのものは `issue/2026/07/1518-purpose-statement.md` の入口基準として定義が確定した。1 issue = 1 意図（PR 並みの粗さ）であり、独立に採否を判断できる問題は束ねず、意図に従属する軽微修正の同乗は許す。

## 変更方針  〔解 / polish〕
規範の本体は purpose-statement が detail の目的節に書く。
本 issue はその検査を create と polish に足す。

- create の妥当性吟味の段に「独立に採否・完了を判断できる問題が複数含まれていないか」の検査を加え、含まれていれば分割した起票を提案する。
- polish の入口の問題空間点検に同じ検査を加え、発覚したら分割の差し戻しを提案する。
- ユーザーが明示的に束ねる指示をした場合は従い、束ねた事実と理由を「人間が決めた判断」に記録する。
- 意図に従属する軽微修正の同乗は違反ではないことを、検査の説明に添える。

検討した代替案と却下理由。

- 行数などの機械的閾値で判定する。粒度は量ではなく採否の独立性で決まるため却下。表記ゆれの一括修正は大きくても1意図である。
- 検査を独立スキルにする。1段の検査のためにスキル境界を増やさないため却下。

## 対象範囲・対象ファイル  〔解 / polish〕
- `.coff/src/coff-issue-create.skill.md`（妥当性吟味への検査追加）
- `.coff/src/coff-issue-polish.skill.md`（入口点検への検査追加）
- `/coff-compile` で反映する
- 実装は purpose-statement の後に行う。規範の本体（detail の目的節）が先にないと、検査が参照先を失う。

## 実装詳細  〔解 / polish〕
- create 手順4（妥当性の吟味）に検査と分割提案を1文で足す。
- polish 手順2（問題空間の点検）に同じ検査を足す。
- 検査の文言は detail の目的節の「1 issue = 1 意図」を参照し、判定基準を二重に定義しない。

## テスト方針  〔解 / polish〕
- 独立な複数問題を含む依頼（0222 相当）を create に与え、分割提案が出ることを確認する。
- 1意図に従属する複数変更（表記ゆれの一括修正など）では分割提案が出ないことを確認する。
- 明示的に束ねる指示を与え、「人間が決めた判断」に記録されることを確認する。

## 人間が決めた判断  〔横断〕
- 判定基準は「1 issue = 1 意図」（PR 並みの粗さ）とし、独立に採否を判断できる問題は束ねない。軽微修正の同乗は許す（2026-07-16。規範の記録本体は purpose-statement 側）。

## リスク・未解決  〔横断〕
- 「独立に採否を判断できる」の判定には主観が残る。検査は分割の提案にとどめ、最終判断はユーザーに委ねる。
- purpose-statement が未実装の間は検査の参照先がない。実装順（purpose-statement が先）で解消する。
