# 実装詳細の節に書ける内容を限定する

issue の「実装詳細」が、手順やスキル本文の下書きの置き場になっている。
書ける内容を「触るソースと順序、後で効く制約」に限定し、手順や本文の下書きを禁じる。

## 目的

実装詳細を、新鮮な実装者が触るソースを探さずに済む対応表にとどめる。
解けた状態では、polish は実装詳細を数行で書き、実装者は done 前の実態合わせをほぼ要しない。

## 現状

`.coff/src/coff-detail-issue.skill.md` のテンプレートは、実装詳細の説明を「触る範囲と代表的なファイルパス、手順、データ構造、インターフェース。単体で実装できる粒度で」としている。
同じファイルの「残す / 溜めない」は「スキルやコードの手順の丸写し」を溜めないと定めており、説明文と矛盾している。
`issue/2026/07/2700-review-diff-code.md` の実装詳細は「手順の骨子」としてスキル本文の下書きを含み、実体はスキル側にある。
`issue/2026/09/1413-issue-template-for-human-reader.md` の実装詳細はソースごとの変更点の一覧だけで、実装後の書き換えは語句の追加にとどまった。
detail は done 前に実装者が実装メモを実態に合わせて書き換えるよう求めており、手順を書いた issue ほど差分の写しを保守する費用が生じる。

## 設計方針

detail のテンプレートで、実装詳細の説明文を「触るソースを反映順に『パス：反映する変更を一言』で。続けて後で効く制約。手順や下書きは書かない」に差し替える。
実体は実装後のスキルとコードにあり、issue に書くと差分の写しを保守することになるからである。
規則の本文はテンプレート規則の段落に置き、説明文は他の節と同じく短い見本にとどめ、後で効く制約の定義は「残す」、禁止の理由は「溜めない」を指して一本化する。
「溜めない」の丸写しの項に下書き（手順の骨子、条文案、コードの草案）を加え、polish の実装者シミュレーションで、手順の曖昧さの解消先を「完了条件の確認手段」と定め、実装詳細に手順が流れる経路を塞ぐ（本 issue の意図に従属する軽微修正として同乗）。
却下した案。

- 節そのものを消す。この repo は `.coff/src/`、`.claude/`、`skills/` の三重構造で、意図がどのソースに落ちるかの一覧は探索を省くので残す。
- polish の自己レビューに点検項目を足すだけにする。テンプレートの説明文自体が手順を書くよう誘導しているので、点検の強化では止まらない。
- 説明文の「単体で実装できる粒度で」を残す。単体で着手できることは polish の出口基準が issue 全体に課しており、実装詳細だけに求めると手順を書く口実になる。

対象外。

- 「完了条件の確認手段」は手順を書く節であり、そのまま残す。
- done 済みの旧 issue は書き換えない。記録の正しさは master に入った時点で判定する（detail の目的節）。

## 決めたこと

- 実装詳細の節は消さず、書ける内容を限定する

## 完了条件

- [x] detail の「溜めない」に、スキル本文やコードの下書きが含まれる
- [x] ビルド済みの `.claude/skills/coff-detail-issue/SKILL.md` と配布用 `skills/coff-detail-issue/SKILL.md` に反映されている

## 実装メモ

### 実装詳細

- `.coff/src/coff-detail-issue.skill.md`：テンプレートの `### 実装詳細` 直下の説明文の差し替え。テンプレート規則の段落群の、完了条件の段落の後に「実装詳細:」の段落を追加。「溜めない」の丸写しの項に下書きを追加。
- `.coff/src/coff-issue-polish.skill.md`：手順 10 の指摘の解消先に、手順の曖昧さは「完了条件の確認手段」へ、の一句を追加。

### 完了条件の確認手段

1. `.coff/src/coff-detail-issue.skill.md` の `### 実装詳細` の次行を読み、「パス」「一言」「制約」「手順」「下書き」の語があり、「データ構造」「インターフェース」「単体で実装できる粒度」が無いことを見る。
2. 同ファイルの「溜めない」の行を `grep '下書き'` し 1 件以上あることを見る。
3. `/compile` 後、`.claude/skills/coff-detail-issue/SKILL.md` と `skills/coff-detail-issue/SKILL.md` を `grep -c '下書き'` し、いずれも 1 件以上あることを見る（テンプレートのコードブロックは英訳されないので、説明文の語がそのまま残る）。
4. scratchpad に一時 git リポジトリを作り、更新後の `.claude/skills/` から coff-detail-issue、coff-issue-create、coff-issue-polish をコピーし、要望に合う README を置く。それだけを読む新鮮なサブエージェントに架空の小さな要望（例: README に使い方の節を足す）で create と polish を実行させる。サブエージェントは非対話なので、ユーザーへの問答は推奨案で自己決定させ、polish 手順 10 の実装者シミュレーションは省かせる。生成物の `### 実装詳細` から次の `###` までを取り出し、`grep -cE '^ *[0-9]+\.'` が 0 であること、各行が `- ` で始まる「パス：一言」か制約の記述であることを目視する。
