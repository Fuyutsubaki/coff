# issue をユーザーが数分で読める形に作り直す

issue テンプレートを、ユーザーが読む上半分と実装者が読む下半分に分け、節名を元ネタの時雨堂に揃える。
決めたことは 1 決定 1 行にし、未決は判断待ちだけに限り、一覧スキルを足す。

## 目的

別リポジトリ mitu3 で codex が coff の issue スキルで作った 13 件の issue が、読みづらく使いづらかった。
原因は書き手ではなく、テンプレートとスキルの規則にある。
ユーザーが open の issue を数分で読め、実装 AI が同じファイルの下半分だけで着手できる状態にする。

## 現状

- テンプレートは 9 節固定で、create は polish 担当の節にプレースホルダを置く。mitu3 では 3 件が 4 節ともプレースホルダのまま残り、1 件は 723 行の設計書になった。
- 「人間が決めた判断」は「発話の粒度・語彙のまま」書く規則で、mitu3 では 1 件に 25 段落の応答記録（「うん」「OK」と回答した）が並んだ。
- 検証は「条件 — 確認: 手段」の 1 行書式で、mitu3 では最長 500 字の行になった。
- 要約は polish が最後に書くため未 polish の issue では空で、一覧を出す手段も無い。
- 実装者シミュレーションの指摘が本文全体に反映されて issue が膨らみ、「リスク・未解決」に懸念と感想が溜まる。done 後の本文と実態の食い違いは「人が直す」とだけ書かれている。

## 設計方針

上半分（目的 / 現状 / 設計方針 / 決めたこと / 未決 / 完了条件）をユーザー向けに 1 画面へ収め、`## 実装メモ` から下を実装者向けにする。
節名は元ネタである時雨堂の issue（目的 / 現状 / 設計方針 / 完了条件）に揃え、空の節とプレースホルダを置かない。

- 決めたことは 1 決定 1 行。応答の記録は書かない。理由をすり替えない規則は残す。
- 未決はユーザーの判断待ちだけ。polish と done の出口で空にする。
- 完了条件は条件を上に、確認手段を実装メモに置く。
- 実装者は done を呼ぶ前に、設計方針と実装メモを実態に合わせて書き換える。積み残しは別 issue に切る。
- 一覧は coff-issue-list を新設して都度出力する。
- 任意節（決めたこと、未決、調査記録、参考）は無ければ置かない。issue では固有名を具体名で書き、coff-japanese-tech-writing の「固有名を出さない」規則を適用しない。

却下した代替案。設計詳細を `docs/` に出す（置き場の規約が増える）。`issue/README.md` を create と done が更新する（陳腐化する）。done 前に「計画から外れた点」「積み残し」を追記する（役に立つ場面が思い当たらない）。

## 実装メモ

### 実装詳細

- `.coff/src/coff-detail-issue.skill.md`：目的節に読者の定義、テンプレート差し替え、決めたこと・未決・完了条件・折り目・done 前の実態合わせの規則。
- `.coff/src/coff-issue-create.skill.md`：要約を create が書く。プレースホルダを置かない。
- `.coff/src/coff-issue-polish.skill.md`：調査記録の置き場、未決の出口、完了条件の上下分離、自己レビュー項目、シミュレーション指摘の行き先。
- `.coff/src/coff-issue-done.skill.md`：完了条件の節名、未決が残っていれば保留、食い違いの直し手は実装者。
- `.coff/src/coff-issue-list.skill.md`：新設。`issue/**/*.md` を走査し status、パス、タイトル、要約（タイトル後の最初の本文行）を表で出す。
- `.coff/src/coff-init.skill.md`：導入対象と CLAUDE.md 追記に coff-issue-list を足す。
- ビルドは `/compile`。`.claude/skills/` と配布用 `skills/` の両方に出る。

### 完了条件の確認手段

1. `.claude/skills/coff-detail-issue/SKILL.md` のテンプレート部分を `grep '^## '` し、要約・背景・目的・変更方針・実装詳細・検証・人間が決めた判断・リスク・未解決・参考・関連 issue が無いことを見る。
2. scratchpad に一時 git リポジトリを作り、新しいスキルだけを読む新鮮なサブエージェントに架空の小さな要望で create と polish を実行させる。生成物を `grep -c '解決空間\|polish で詰める'` し 0 であること、`## 実装メモ` の行番号が 50 以下であること、決めたことを `grep '回答した\|肯定した'` して 0 件であること、`### 完了条件の確認手段` が存在することを見る。
3. `/coff-issue-list all` を coff で実行し、既存 17 件と本 issue が並び、要約列が空でないことを見る。
4. 本 issue に対して `/coff-issue-done` を実行し、完了条件のボックスで判定されることを見る。
5. `gh skill publish --dry-run` を実行し、出力に coff-issue-list が含まれることを見る。
