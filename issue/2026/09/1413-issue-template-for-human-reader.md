# issue をユーザーが数分で読める形に作り直す

issue テンプレートを、ユーザーが読む上半分と実装者が読む下半分に分け、節名を元ネタの時雨堂に揃える。
決めたことは人間の判断が入った点だけに絞り、未決は判断待ちだけに限り、一覧スキルを足す。

## 目的

別リポジトリ mitu3 で codex が coff の issue スキルで作った 13 件の issue が読みづらく使いづらかった。原因は書き手ではなく、テンプレートとスキルの規則にある。
ユーザーが open の issue を数分で読め、実装 AI が折り目より下まで読めば着手できる状態にする。

## 現状

- テンプレートは 9 節固定で、create は polish 担当の節にプレースホルダを置く。mitu3 では 3 件が 4 節ともプレースホルダのまま残り、1 件は 723 行の設計書になった。
- 「人間が決めた判断」は「発話の粒度・語彙のまま」書く規則で、mitu3 では 1 件に 25 段落の応答記録が並んだ。
- 検証は「条件 — 確認: 手段」の 1 行書式で、mitu3 では最長 500 字の行になった。
- 要約は polish が最後に書くため未 polish の issue では空で、一覧を出す手段も無い。実装者シミュレーションの指摘が本文全体に反映されて issue が膨らみ、「リスク・未解決」に懸念と感想が溜まる。
- done のゲートは本文と実態の食い違いを見つけても本文を書き換えず、人が直すかリスクへ移すかを判断する、とだけ定めている。

## 設計方針

上半分（要約 / 目的 / 現状 / 設計方針 / 決めたこと / 未決 / 完了条件）をユーザー向けに 1 画面へ収め、`## 実装メモ` から下を実装者向けにする。節名は元ネタである時雨堂の issue に揃え、空の節とプレースホルダを置かない。

- 要約は create が書く。任意節（決めたこと、未決、調査記録、参考）は無ければ置かない。固有名は具体名で書き、coff-japanese-tech-writing の「固有名を出さない」規則を適用しない。
- 決めたことは日付なしで、AI の推奨と違う選択と人間に委ねた選択だけを書く。応答の記録は書かない。理由をすり替えない規則は残す。
- 未決はユーザーの判断待ちだけ。polish と done の出口で空にする。
- 完了条件は条件を上に、確認手段を実装メモに置く。0200 の「簡潔さのために削らない」は残す。
- 実装者は done を呼ぶ前に、設計方針と実装メモを実態に合わせて書き換える。残作業は別 issue に切る。done の出口基準を detail に足す。
- 旧テンプレートの issue は書き換えない。polish を通したときだけ新テンプレートに書き換える。
- 一覧は coff-issue-list を新設して都度出力する。却下した代替案は決めたことにある。

## 決めたこと

- 実装者向けの詳細は同じファイルの末尾に置く（`docs/` に出すと置き場の規約が増える）
- 命名と配置は現行のまま（変える理由が無い）
- 一覧は README を置かず、スキルで都度出力する（README は陳腐化する）
- done 前に設計方針を実態に合わせて書き換える。計画から外れた点と積み残しは書かない（役に立つ場面が思い当たらない）
- 決めたことに承認された推奨は書かない（設計方針と食い違うのはおかしい。日付付きで並べると議事録になる）
- 設計 issue と実装 issue を分ける規律は足さない（既存の分割提案で足りる）
- 一覧スキルは LLM の手順にせず、埋め込みコマンドで bash を実行するだけにする（一覧に判断は要らない）

## 実装メモ

### 実装詳細

- `.coff/src/coff-detail-issue.skill.md`：目的節に読者の定義、テンプレート差し替え、決めたこと・未決・完了条件・折り目の規則、done の出口基準と done 前の実態合わせ、固有名の適用除外。
- `.coff/src/coff-issue-create.skill.md`：要約を create が書く。現状は事実だけ。プレースホルダを置かない。
- `.coff/src/coff-issue-polish.skill.md`：調査記録の置き場、未決の出口、完了条件の上下分離、自己レビュー項目、シミュレーション指摘の行き先（fork でない新鮮なサブエージェント）、旧テンプレートの書き換え。
- `.coff/src/coff-issue-done.skill.md`：完了条件の節名、未決が残っていれば保留、食い違いの直し手は実装者。
- `.coff/src/coff-issue-list.skill.md`：新設。LLM の手順ではなく、埋め込みコマンド（`!` バッククォート）の awk 1 本で `issue/*/*/*.md` から status、パス、タイトル、要約（タイトル後の最初の本文行）を表にする。`allowed-tools: Bash(awk *)` で前もって許可する。
- `.coff/src/coff-init.skill.md`：導入対象と CLAUDE.md 追記に coff-issue-list を足す。
- ビルドは `/compile`。`.claude/skills/` と配布用 `skills/` の両方に出る。

### 完了条件の確認手段

1. `.claude/skills/coff-detail-issue/SKILL.md` のテンプレート部分を `grep '^## '` し、要約・背景・目的・変更方針・検証・人間が決めた判断・リスク・未解決・参考・関連 issue が `##` として無いことを見る（`実装詳細` と `参考` は `###` として残る）。
2. scratchpad に一時 git リポジトリを作り、新しいスキルだけを読む新鮮なサブエージェントに架空の小さな要望で create と polish を実行させる。生成物を `grep -c '解決空間\|polish で詰める'` し 0 であること、`## 実装メモ` の行番号が 50 以下であること、決めたことを `grep '回答した\|肯定した'` して 0 件であること、`### 完了条件の確認手段` が存在することを見る。
3. `/coff-issue-list all` を coff で実行し、既存 17 件と本 issue が並び、要約列が空でないことを見る。`gh skill publish --dry-run` を実行し、警告なく完了することを見る。
4. 本 issue に対して `/coff-issue-done` を実行し、完了条件のボックスと未決の有無で判定されることを見る。
