# polish に、清掃の手順と実装前のレビューを加える

polish を終えた issue に経緯の記述や古くなった前提が残り、設計の過剰さや複雑さは実装後のレビューで初めて見つかっている。
polish に、書いた内容を清掃する手順と、実装者シミュレーションの後に issue と実装計画をレビューする手順を加える。

## 目的

open の issue は、依頼者が折り目より上を数分で読み、実装者が単体で着手する仕様であり、polish の出力にある次の 2 つの問題がこの使い方を妨げている。

- 記録の質：経緯が書き込まれ、古くなった記述が残る。依頼者は読む量が増え、実装者は崩れた前提のまま着手する。解けた状態では、各記述が今回の決定と矛盾せず、現在の仕様として読める。
- 設計の質：過剰な機能、無意味に複雑な仕様、ユーザー入口の不備が実装後のレビューまで見つからず、見つかった時点で実装をやり直すことになる。解けた状態では、この種類の問題が実装の前に依頼者へ届く。

## 現状

- dullmify skill の issue（1623-dullmify-skill.md。master には無く、`issue/dullmify-skill` ブランチに残る）を、実装を破棄して open に戻し、polish した。要約とタイトルは経緯を語り、「決めたこと」は決めた順に足されて 22 行になった。完了条件、却下理由、実装メモには以前の実装の前提が残り、折り目より上は約 80 行あった。見つけたのは依頼者と実装者シミュレーションで、polish は行数の超過を直さず残課題として報告した。
- 同じ issue は、実装後のレビューで設計が 5 回変わった（runtime の削減、driver の統合、引数の変更、独立 skill 化、coff-compile への適用見送り）。`issue/2026/09/1413-issue-template-for-human-reader.md` でも、実装後のレビュー 2 回で依頼者の判断が要る点が 7 つ出た。どれも `.coff/src/coff-review-diff-code.skill.md` の観点 2、3、4、6 が拾う種類の問題である。
- `.coff/src/coff-issue-polish.skill.md` の前提検証（手順 4）は、記述と現在のコードの矛盾だけを見る。自己レビュー（手順 8）の「後で読む人に無用な、またはすぐ古くなる情報を書いていないか」は、点検する対象を挙げていない。実装者シミュレーション（手順 10）は、issue 単体で着手できるかだけを問う。実装者役は設計を正しいものとして計画を立てるので、設計の過剰さは見ない。返ってきた実装計画は、着手の可否を見たあと使われない。
- `.coff/src/coff-detail-issue.skill.md` は「決めたこと」に載せる基準を定めるが、行の書き換え、削除、並べ方は定めず、横断の節は「書き足す」としている。「溜めない」に挙がる経緯は、セッションの経緯に限られる。折り目より上の目安（50 行）は polish の出口に入っていない。

## 設計方針

清掃は polish 自身の手順にし、issue ファイルを書き出した後、実装者シミュレーションの前に、書き出した全文を対象に行う。書き出し前の自己レビューは清掃にまとめる。
点検する対象を手順に挙げる。タイトルと要約、決めたこと、完了条件と確認手段、却下理由、実装メモ、折り目より上の行数である。
何を残し何を消すかの規則は detail に置く。「決めたこと」は今有効な決定の一覧として手入れし、どの節も「決めたこと」と設計方針に矛盾させず、「溜めない」の経緯は以前の実装や polish の経緯まで広げる。polish の出口には、折り目より上が目安の行数に収まることを足す。

レビューは毎 polish で 1 回、実装者シミュレーションの後に行う。新鮮なコンテキストの subagent を観点ごとに並列に立て、issue ファイルと、最後のシミュレーションが返した実装計画だけを渡す。
観点は次の 5 つに固定する。YAGNI、仕様が無意味に複雑でないか、目的と変更規模の釣り合い、ユーザー入口（計画に含まれるか、仕様の写しで肥大していないか）、記録としての質（経緯の記述、節どうしの矛盾、古い前提）である。
指摘は polish の論点の仕分けで扱い、的外れな指摘は捨て、判断の要らないものは polish が直し、依頼者の判断が要るものはその場で聞く。

- 却下：レビューを別 skill に切り出す。単独で呼ぶと実装計画が無く、skill の中でシミュレーションをやり直すことになって polish と重なる。
- 却下：観点を coff-review-diff-code と共有する。対象が差分ではなく issue と計画なので、観点 1 と 5 が使えず、残りも文言が変わる。

## 決めたこと

- 清掃とレビューを 1 つの issue で扱う（polish の改善として立てた issue なので）
- 議事録にしようとする傾向をやめさせ、清掃の手順を明示的に入れる（後から見て役に立つ形式になっておらず、古い記述を平気で残すので）
- 実装者シミュレーションの後に、polish の手順として、観点ごとに並列に立てた subagent が issue と実装計画を 5 観点でレビューする（実装後のレビューで初めて見つかる issue レベルの問題が多すぎるので）
- 「決めたこと」は載せる基準を変えず、今有効な決定の一覧として手入れする。置き換わった行は書き換え、対象がなくなった行は消し、同じ主題は 1 つの決定にまとめ、主題の順に並べ、経緯は書かない

- [x] detail が、「決めたこと」の手入れ、どの節も決めたことと設計方針に矛盾させないこと、以前の実装や polish の経緯を溜めないこと、polish の出口の行数を定めている
- [x] 経緯、古い前提、過剰な拡張点を仕込んだ issue を polish すると、清掃かレビューがそれぞれを取り除くか指摘する

## 実装メモ

### 実装詳細

- `.coff/src/coff-detail-issue.skill.md`：「決めたこと」の規則に手入れを足す。設計方針と「決めたこと」の間に限っている矛盾の禁止を、全節に広げる。「溜めない」の経緯を広げる。「問題空間と解決空間」の節の「書き足す」を手入れと矛盾しない言い方に改める。polish の出口に折り目より上の行数を足す。
- `.coff/src/coff-issue-polish.skill.md`：書き出しの段とシミュレーションの段の間に清掃の段を足し、書き出し前の自己レビューをそこにまとめる。シミュレーションの後にレビューの段を足す。
- `.coff/src/coff-issue-done.skill.md`：coff-review-diff-code を案内する条件を「実装後の差分の多観点レビュー」が未実施のときと書き分ける（polish を経た issue は実装前のレビューを受けているので、区別しないと案内が省かれる）。
- `/compile`：成果物 `.claude/skills/` と配布ミラー `skills/` を更新する。

制約は次のとおり。

- 清掃を書き出しの後に置くのは、要約とタイトルが書き出しの段で確定するからである。今回のセッションで書いた分も対象にする（1623 の経緯の記述は、引き継いだ分ではなく、そのセッションで書かれた）。
- 清掃とレビューの「記録としての質」は同じ規則で見るが、重複させている。経緯の記述や古い前提は、書いた本人より会話を知らない読み手のほうが見つけやすい（1623 で見つけたのも依頼者と実装者シミュレーションだった）。
- polish は detail の規則を再掲しない（polish ソースの先頭コメントの方針）。清掃の段は点検の対象を挙げ、残すか消すかの判断は detail の規則に委ねる。
- レビューの指摘を直す場所は折り目の上下を問わない。シミュレーションの指摘は着手の妨げなので原則として実装メモで解消するが、レビューの指摘は設計そのものを対象にするからである。
- 折り目より上の行数は `## 実装メモ` の行番号で数える（frontmatter と空行を含む。`issue/2026/09/1413-issue-template-for-human-reader.md` の確認手段と同じ数え方で、行番号が 50 以下なら収まっている）。50 行は目安のままにし、polish は超過を残課題として報告せず、要約度を上げて直す。
- subagent はネイティブのものを既定にし、codex-delegate は代替にとどめる（`issue/2026/07/1518-polish-implementer-sim.md` の判断）。

### 完了条件の確認手段

1. `.coff/src/coff-issue-polish.skill.md` を読み、清掃の段が書き出しの段とシミュレーションの段の間にあり、設計方針に挙げた 6 つの対象と、以前の自己レビューの 2 項目を含むことを確かめる。レビューの段がシミュレーションの後にあり、5 観点、渡す入力、1 回限りであること、シミュレーションのやり直しの条件が分かることを確かめる。
2. `.coff/src/coff-detail-issue.skill.md` を読み、4 つの規則があることを確かめる。
3. `/compile` の後に行う。検証用の issue を subagent にスクラッチ領域へ 1 つ作らせる（コミットしない）。題材はこのリポジトリに実在する skill への小さな変更にし、polish 済みの体裁にさせる。要約に経緯の文、「決めたこと」に対象のない行、完了条件に「決めたこと」と矛盾する前提、設計方針に使い道のない拡張点を仕込ませ、仕込みの一覧は別ファイルに書かせ、報告では 2 つのパスだけを返させる。実装したセッションは一覧を読まずに、検証用の issue を引数に `/coff-issue-polish` を実行する。終わってから一覧と突き合わせ、4 点が取り除かれたか、レビューの指摘（依頼者への問いを含む）として現れたことを確かめる。
4. 各成果物の末尾の md5 がソースの `md5sum` と一致し、`cmp .claude/skills/<name>/SKILL.md skills/<name>/SKILL.md` が両 skill で一致することを確かめる。
