# polish の点検を、実装で初めて分かる設計の穴に届かせる

polish の試験実装・実装者シミュレーション・観点別レビューは、issue に書かれた設計の範囲でしか点検しない。
実装で設計が変わったときに戻る道がなく、故障時の振る舞いを問う観点もなく、試験実装の入力が浅いと本番で当たる制約を見逃す。

## 目的

polish を通した issue でも、実装に入ってから設計の穴が見つかり、実装セッションの中で設計を変えて進めることがある。そのとき変えた設計は polish の点検を受けないまま実装され、実装後のレビューで、古くなった記述と規約の穴がまとめて出る。
解きたい問題は、polish の点検が「issue の文面どうしの整合」に閉じていて、実装で初めて分かることに届かないことである。解けた状態は、次の 3 つが polish の手順に組み込まれていることである。

- 実装中に設計方針か完了条件を変えたら、変えた issue を手順 10（実装者シミュレーション）と 11（レビュー）に戻す道がある。
- レビューの観点に、故障時の振る舞い（プロセスが殺されたとき、書くべきものがないとき、外部コマンドが失敗したとき）を問うものがある。
- 試験実装は、本番に近い中身で行う（短い定型の入力で通っただけでは合格にしない）。

3 つを polish skill の 1 回の改訂で扱うか、独立に採否を判断して分けるかは未決に置く。

棄却した捉え方: レビューの回数を増やせば拾えるという見方は採らない。今回の 2 回目のレビューで出た指摘の大半は、設計変更の後始末（古い記述）と、変更後の規約の穴で、回数ではなく「変更を点検に戻す」ことの問題だった。

## 現状

- polish の手順は `.coff/src/coff-issue-polish.skill.md` にある。手順 7（試験実装）は「実現可能性が不確かな箇所は小さく試して確かめる」とだけ定め、入力の深さを定めない。手順 10 は issue だけを読むサブエージェントに「実装計画の骨子 / 着手を妨げる点 / 曖昧な点 / 完了条件が実行可能か」を返させる。手順 11 の観点は YAGNI、複雑さ、規模の釣り合い、ユーザー入口、記録としての質の 5 つで、故障時の振る舞いを問う観点はない。「設計方針か完了条件を変えたら手順 10 をやり直す」は polish の中でだけ効き、実装セッションには規定がない。
- issue/2026/09/2200-add-dullmify.md（dullmify）で起きたこと:
  - 調査記録 4 の試作は、heredoc で短い引数を渡して通った。実装で C++ の関数本体を同じ経路に流したところ、Claude Code の Bash ツールが `{`、引用符、`}` を含むコマンドを静的に拒否し（調査記録 6）、当初の受け渡し方式は一度も動かなかった。
  - 受け渡しをファイルに変え、さらに起動スクリプトを `start` / `continue` に変えた（決めたこと、調査記録 9）。この変更は実装セッションで issue を書き換えて進め、手順 10〜11 は通していない。
  - 変更後の coff-review-diff-code（2 回目）は約 40 件を返した。動かして再現した欠陥は 5 件で、残りは設計変更で古くなった記述（設計方針 4、補助関数の説明、確認手段の文言）と、変更後の規約の穴（exit 2 の使い方が二重、stderr が行動を示さない場合、答えを記録した直後に殺された場合）だった。後者 2 種は、変更した issue を手順 10〜11 に通していれば polish の段で出る種類である。
  - 答えを記録した直後にプロセスが殺される場合は、issue の調査記録 2 と 3（サンドボックスが呼び出し終了時にプロセスを殺す）から推論できたが、polish の観点にその問いがなく、初回の polish では出なかった。
- coff-review-diff-code の観点 1（一般）は、issue が脅威モデル（不注意な生成コードを止める。回避を狙うコードは対象にしない）を書いていなかったため、拒否リストの迂回を探し続けた。issue 2200 には実装後に脅威モデルの一文を足した。polish の段で脅威モデルの明示を求める観点はない。

## 未決

- 3 つの改訂（設計変更時の戻り、故障時の観点、試験実装の入力の深さ）を 1 つの issue で扱うか、独立に採否を判断して分けるか。
