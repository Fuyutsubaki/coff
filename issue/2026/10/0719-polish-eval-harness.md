# polish の既知の失敗が再発しないことを、固定した題材で測れるようにする

polish の点検を少数の原則にまとめる改訂（issue/2026/09/2908-polish-principles-over-checklist.md）は、チェック項目を減らす。
減らしても dullmify で起きた失敗が戻らないことを確かめる手段がないので、polish 自体を被験体にした回帰評価を `.coff/test/coff-issue-polish/` に置く。

## 目的

polish skill の本文は、誰にも評価されていない。
手順 10 と 11 の新鮮なサブエージェントは polish が書いた issue を点検するが、polish の手順書そのものが実行者にどう読まれ、どこで裁量が入るかは測っていない。
dullmify の issue で起きた失敗（ユーザーに聞くべき選択を黙って決めた、採用理由を残さなかった、調査記録が文書だけで不正確だった、API の根本を問わなかった）は、issue の文面どうしの整合を見る点検では出ない種類のものだった。
2908 はこの失敗を少数の原則にまとめて防ぐと決めたが、項目を減らす改訂は、既知の失敗が戻っても気づけない。

解きたい問題は、polish の改訂が既知の失敗を再発させていないかを、改訂のたびに確かめる手段がないことである。
解けた状態は次の 3 つが成り立つことである。

- わざと穴のある issue 草稿（題材）と、polish が出すべき判断の期待値が、被験エージェントから見えない形で `.coff/test/coff-issue-polish/` にある。
- 会話を継承しない新しいエージェントに polish を走らせ、期待値との一致と、polish の指示のうち不明瞭だった箇所と裁量で補った箇所の自己申告を得られる。
- 2908 の改訂を、この評価の前後比較で確かめられる。

扱わないこと: polish 本文の原則化は 2908 が、実装中に設計が変わったときに polish へ戻す道は issue/2026/09/2801-polish-reach-implementation-findings.md が扱う。

棄却した捉え方が 2 つある。
失敗例を手順 9 と 11 の項目として skill 本文に足す形は、2908 が棄却している（項目を足すたびに skill が長くなる）。
dullmify の issue の初期版（コミット 06d0f65）をそのまま題材にする形も採らない。
初期版は設計方針と決めたことを既に持つ「失敗した polish の成果物」で、「決めたこと」を再質問させる期待値は coff の規約（決めたことはユーザーの判断）と衝突し、今の作業ツリーで走らせると完成版の dullmify と 2908 から正解を読めてしまう。

## 現状

- polish の手順は `.coff/src/coff-issue-polish.skill.md` にある。手順 5 で一問ずつユーザーに聞くので、評価用のサブエージェントにそのまま走らせることはできない（サブエージェントは人に質問できない）。
- LLM を使う評価の前例は `.coff/test/coff-dullmify/` にある（`review-tests.sh` が点検役の合否を良い題材と悪い題材で確かめる）。dullmify の issue（issue/2026/09/2200-add-dullmify.md）の調査記録 15 と 16 に、同じ題材で点検役の合否が揺れた記録がある。
- 2908 は、dullmify で見つかった 7 点を skill 本文ではなく回帰評価の入力として残す案を未決に置いていた。本 issue がその置き場になる。
- 計測の経路は agent ごとに違う。Claude Code では Agent の結果から取る。codex では `codex exec --json --ephemeral` が `turn.completed` にトークン使用量を、`command_execution` の件数にコマンド実行数を出し、`--output-schema` で最終応答の形を JSON Schema で強制できる（codex-cli 0.153.4、2026-10-07 確認）。所要時間はイベントにないので呼び出し側で取る。

## 実装メモ

### 調査記録

- mizchi「プロンプトの再現性をAI に自動チューニングさせる方法 ~ 暗黙知を排除する」（https://zenn.dev/mizchi/articles/empirical-prompt-tuning、2026-10-07 閲覧）。固定したシナリオ（典型 1 とエッジ 1〜2）と `[critical]` 付きの要件チェックリストを置き、会話を継承しない新規エージェントに対象プロンプトを実行させて「成果物、要件達成、不明瞭点、裁量で補った箇所、再試行回数」を報告させる。併せて tool 使用数、所要時間、トークン数を機械的に取る。1 回に 1 箇所だけ直して必ず新規エージェントで再実行し、連続 2 回で新規の不明瞭点ゼロと指標の頭打ちが揃ったら止める。hold-out シナリオで大きく落ちなければ過適合なしとみなす。限界として、設計方針そのものが誤っているプロンプトはパッチで直らないこと、3 並列で 1 回あたり各 3 万トークン程度かかることを挙げる。
- codex への相談結果（2026-10-07、gpt-5.6-sol、`codex exec -s read-only` に記事全文と本リポジトリを読ませた読み取り専用の相談）。外部評価ループは使う価値があるが、「問いを何個拾えたか」を測ると質問過多な polish に最適化される、という回答。
  - 乾式では問いの一覧ではなく判断台帳を出させる。論点ごとに、出所（コード、ユーザー決定、文書、実測、推論）、別案なら issue のどこが変わるか、処置（調査する、聞く、決定済みとして進める）、推奨案と理由、先に決める論点を返させ、評価モードではファイルを編集せず最初の質問の直前で止める。加えて、問題と現状だけから再導出した最小の解決モデル、実測が必要な主張、質問しないと判断した論点と理由、不明瞭だった skill の指示、裁量で補完した箇所を返させる。
  - 主指標は、必要なユーザー判断の再現率、不要な質問の少なさ、コードで答えられる論点を調査へ回した割合、出所のない確定の数、根本モデルを問い直せたか、回答後の issue の整合性。tool 使用数と時間は同一基盤内の診断値にとどめ、Claude Code と codex の値は混ぜない。
  - 手順 10 と 11 を常に省くと、2908 の原則 B（採用案を見せずに再導出する独立設計役）を測れない。毎改訂で回す乾式（手順 2〜6 相当）と、大きな変更時だけ回す end-to-end（手順 10 と 11 を含む）に分ける。手順 9 は issue を書かない乾式からは外す。
  - 題材は最低 4 ケース。dullmify（調整用）、別分野の hold-out（根本モデルと技術選定を含むが JSON や C++ は出てこない）、コードで答えが出る論点だけのケース（人間に聞かないことを確かめる）、判断済みの issue（同じ選択を再質問しないことを確かめる）。増やし方は mutation testing で、良い issue の写しに欠陥を 1 つだけ入れる（採用理由だけを削る、決めたことから 1 項目を外す、実測を文書由来の断定に変える、問題から導けない API を 1 つ仮置きする）。同じ技術選択を一方は未承認、他方はユーザー決定済みにした対照ケースを重視する。
  - チェックリストは dullmify 固有の語ではなく概念で採点する。例: 別案に替えると設計方針、完了条件、確認手段が変わる未承認の選択を黙って確定しない。目的と現状から、保持すべき状態、基本操作、副作用の境界を独立に再構成する。誤りなら設計が変わる技術的主張について、安全に可能なら実測を提案または実行する。コードで答えられることと明示的に決定済みのことをユーザーに聞かない。
  - 対話評価は LLM にユーザー役を自由に演じさせると不備を救済するので、問いを意味カテゴリに分類して固定回答を返す driver にする。LLM 評価は揺れるので、重要ケースは 2〜3 回走らせて分布を見る。
  - 題材と期待値は被験エージェントから物理的に見えない場所に置く。評価用に再構成した草稿を一時リポジトリに置くか、旧 issue を使うなら「設計方針と決めたことは AI が仮置きした未承認案」と明示する。
  - 外部評価より先に効く安い手として、手順 5 の前に判断台帳を内部生成させること、質問開始前に「問題と現状だけ」を渡す独立設計役を 1 回置くこと、実装中に設計方針か完了条件が変わったら polish に戻すこと（2801）を挙げ、順序は判断台帳、2908 の原則化、代表題材の乾式評価、2801、対話評価が堅実とした。
